## 1. 项目定位：搭建的是怎样的系统

### 1.1 一分钟口述版

> 我在摩尔线程实习期间，围绕 MTT S5000 上的推理服务搭建了多模型自动化性能测试流程，并对照 SGLang 的参考配置和测试结果评估 vLLM-MUSA。系统把服务启动和压测拆开：服务端脚本负责模型配置、GPU 绑定、端口分配、就绪检查和进程管理；压测端按模型、输入输出长度和请求到达速率运行测试，归档吞吐、TTFT、TPOT 等数据。后续扩展了 TP 多卡和基于 MooncakeConnector 的 PD 分离部署。分析中，我重点排查了预热覆盖、固定发压速率不适合不同模型，以及有限请求数带来的吞吐统计偏差，并结合等待队列、KV cache 占用和设备利用率分析性能变化。

主要价值是把“手动起服务、跑几个数字”组织成可配置、可复测、可追溯的测试流程，并解释结果为什么变化。

## 4. 服务层与压测层为什么能分开

### 4.1 服务层负责什么

`run_list.py` 使用 `subprocess.Popen` 启动服务。每个服务配置模型路径、served name、端口、TP、显存预算、block size、Graph 与模型特定参数。

GPU 映射示例：

```text
TP1：模型0 → GPU0，端口8000；模型1 → GPU1，端口8001；最多8组
TP4：模型0 → GPU0～3，端口8000；模型1 → GPU4～7，端口8001
PD + TP4：P → GPU0～3:8100；D → GPU4～7:8200；proxy → :8000
```

脚本同时设置 `CUDA_VISIBLE_DEVICES` 和 `MUSA_VISIBLE_DEVICES`。这是指定进程能看到哪些卡，不是按请求动态分配 GPU 执行单元。`--gpu-memory-utilization 0.8` 是显存预算相关参数，也不是限制只使用 80% 算力。

服务常驻后，由框架内部负责请求排队、调度、KV 分配、模型执行。启动器没有逐请求参与这些决策。

### 4.2 压测层负责什么

`test_list.py` 只需知道地址、端口、模型名和请求协议，就能向已经启动的服务发请求。它不需要知道服务是 TP1、TP4，还是后面挂了 PD proxy。

同一轮通常跨模型并行测试，同一模型的 case 顺序执行。跨模型并行能缩短测试耗时，但 CPU、内存、网络、PCIe/卡间互联可能互相影响；隔离复测才能更可靠地做框架横向比较。

### 4.3 已实现的工程改进

- 每模型独立 case/rate，从参数文件驱动，减少手改脚本。
- 启动参数通过环境变量传递，包含 `AUTOBENCH_MODELS`、`AUTOBENCH_EXTRA_ARGS`、`AUTOBENCH_PARAM_FILE`、`AUTOBENCH_TP` 和 PD 参数。
- 普通服务检查 `/v1/models`，PD 同时检查 P、D 和 proxy 的健康状态。
- 按时间戳归档结果，并保存 `params_snapshot.json`。
- 显示加载与 case 进度；case 进度按 CSV 行数统计。
- 用进程组管理服务生命周期；顶层压测结束后可自动停服务。
- 支持选择模型、dry-run、自定义参数文件、保留服务以及 TP/PD。

当前仍有部署目录硬编码；迁移时要检查多个脚本中的路径，不能只修改顶层 `AUTOBENCH_DIR` 就假设全部依赖都已迁移。

## 5. 请求是怎么进入 GPU 的

```text
压测计划产生请求
  ↓ 可能等待客户端 max_concurrency 信号量
客户端开始该请求计时，发送 HTTP
  ↓ 网络 / proxy / API server
服务端等待队列（CPU 上的请求与调度状态）
  ↓ 检查序列数、token 预算、KV block 等约束
调度到本轮执行
  ↓ 输入准备 / 模型执行 / 采样
GPU 上的权重、激活与 KV cache
  ↓
流式返回 token / 文本块
```

### 5.1 等待队列在显存里吗

等待队列本身主要是 CPU 侧数据结构。请求尚未获得执行资源，不意味着已经为它完整分配了 GPU KV cache；但被暂停/抢占过的请求可能还有缓存相关状态，具体取决于策略。

CPU 队列长度随到达、完成、取消、拒绝而变化，不等于 `max-num-seqs`，也不等于一场压测的 `num-prompts`。API 网关或服务可以另设准入上限，需要单独确认。

等待的请求通常不会直接加入当前 decode 的 GEMM；大量积压仍可能增加 CPU 调度、内存和网络处理负担。不能据此保证“只要在 CPU 队列里，对 GPU 执行速度就完全没有影响”。

### 5.2 一批请求必须都处于同一步吗

不需要。Continuous batching 按迭代更新参与执行的请求，而非固定一批从头一起跑到尾。

```text
某次调度：A decode一个token；B decode一个token；C prefill一个chunk
下一次： A结束退出；B继续decode；C继续prefill；D可能加入
```

一个服务可以同时管理 prefill、decode 和 waiting 请求。支持混合调度时，同一次模型执行可包含两种阶段的 token，但底层 attention 等算子可能再分路径执行。

### 5.3 vLLM 会不会自己发现资源不够

会依据 KV block 可用量、调度 token 预算、序列上限等决定是否能调度请求。它不是只看用户给的 `max-num-seqs`。

但不能把它理解成通用的硬件负载反馈控制器：“发现 SM 达到 90% 就自动停止接纳请求”。算力/带宽不足往往表现为每轮变慢，而非直接触发一个统一的 SM 准入阈值。

### 5.4 暂停、重计算、缓存搬运

| 机制 | 含义 | 对性能的影响 |
|---|---|---|
| 暂停/抢占 | 某请求暂时不继续执行，为其他请求让出资源 | 首 token 前增加 TTFT；开始输出后增加 ITL/TPOT |
| 重计算 | 释放部分缓存后，恢复请求时重新计算所需历史 KV | 节省驻留显存，增加计算和等待 |
| 缓存搬运/offload | 将 KV 搬到其他存储层，使用前再加载 | 节省 GPU 驻留容量，增加传输成本 |

三者有关，但不是同一个操作。官方 V1 文档描述默认抢占采用重计算，不能把早期版本的 CPU swap 当作本环境必然启用的路径。[vLLM 调优文档](https://docs.vllm.ai/en/latest/configuration/optimization/)

## 6. 容易混淆的配置

### 6.1 参数对照表

| 参数 | 控制对象 | 不代表什么 |
|---|---|---|
| `--request-rate` | 客户端请求到达速率，单位 req/s | 并发请求数 |
| `--max-concurrency` | 压测客户端最多同时执行多少个请求函数 | GPU 的最大 batch |
| `--max-num-seqs` | 服务端单轮调度的序列数上限 | QPS、等待队列长度、保证能跑满的 batch |
| `--max-num-batched-tokens` | 单轮模型执行中新调度 token 的预算 | KV cache 中全部历史 token 的总量 |
| `--num-prompts` | 测试总共发多少请求 | 每秒压力、服务端并发上限 |
| `--gpu-memory-utilization` | 引擎显存使用预算相关配置 | GPU 算力利用率上限 |
| `--max-model-len` | 单条序列允许的总长度上限 | 每轮一定计算这么多 token |
| `--block-size` | KV cache 的 token block 粒度 | CUDA thread block 的线程数 |

项目 wrapper 当前没有给正式压测命令传 `--max-concurrency`。压测引擎本身有客户端信号量能力，因此要区别“工具提供”与“这轮实际开启”。

### 6.2 max-num-seqs 大小的影响

上限太小，可能无法形成足够大的 batch，资源利用不足，较多请求等待名额；增加上限可能提升吞吐。

但上限继续增加，吞吐可能趋平，单轮时间和 KV 压力却继续增长，TPOT 变差。比如从 32 增到 64 后 output tok/s 基本不变、TPOT 明显变大，就没有必要仅为了并发数字更高继续增加。

这不是说“把上限设为 64 就必定同时跑 64 条”。实际执行还受到请求数、KV 容量和 token 预算限制。

不能简单断言“上限高只伤 TPOT，上限低只伤 TTFT”：两种延迟都可能变化。没有达到序列上限，也可能因 KV 不足、prefill 被切块或其他调度约束而等待。

### 6.3 max-num-batched-tokens 的例子

假设单轮预算是 2048，新调度的 decode 请求有 100 条，每条本轮计算 1 个 token，则占约 100 个预算，剩余预算可以分配给 prefill。

一个 4096-token 的新 prompt 可能分多轮处理。decode 请求之前已缓存的 10000 个历史 token，不会按 10000 个“新调度 token”扣预算，但 attention 读取这些 KV 仍有真实成本。

投机验证可能每条请求调度多个位置，不能再直接把“序列数”等同于“本轮 token 数”。

chunked prefill 的典型权衡是：prefill chunk 较小，较容易保护 decode 的 ITL；chunk 较大，prefill 可能更快完成，但单轮执行更长。具体效果还受负载和实现影响。[vLLM chunked prefill 说明](https://docs.vllm.ai/en/latest/configuration/optimization/#chunked-prefill)

### 6.4 CUDA/MUSA Graph 的 capture sizes

项目配置了一组尺寸，例如 `1,2,...,8,10,12,...,64,100,128,256`。

它们是运行器用于捕获/选择计算图的离散执行尺寸，不是“生成超过第几个 token 后开始录图”，也不是直接按完整 prompt 长度逐一对应。

普通 decode 每条序列本轮通常一个 token，因此执行 token 数常接近活跃序列数；投机、多 token 调度、不同 graph 模式下不能这样直接等同。运行器可能 padding 到适合的捕获尺寸，不能覆盖的路径可能走其他执行模式，具体看该版本 runner 与日志。

Graph 主要减少 CPU 提交与调度开销；不是自动把所有 kernel 融合成一个，也不会自动消除模型依赖。

### 6.5 本项目发压设置

- `NUM_PROMPTS` 默认 100，可由 `AUTOBENCH_NUM_PROMPTS` 覆盖；后续部分 32B/PD 测试使用 500。
- `random-range-ratio=1.0` 用于固定长度档；chat template/tokenizer 仍可能影响最终输入长度，应核对实际统计。
- `burstiness=102`：Gamma 间隔分布较集中，接近匀速。该参数为 1 时是指数间隔，低于 1 更突发；不是“102 倍突发”。
- Completions 路径默认 temperature=0、默认忽略 EOS，以便控制输出长度。实际输出数量还要核验。
- 预热包含额外按 `(input_len, output_len)` 覆盖的请求，也有每 case 的 warmup 参数；预热结果不计入正式统计。

## 7. TTFT、TPOT、ITL、E2E 的准确口径

### 7.1 时间线

```text
t_plan：计划到达 / 等客户端发送名额
t0：进入请求函数，开始计时，然后发送 HTTP
t_server：服务端收到请求并排队
t1：客户端收到首个非空输出文本块
t2、t3...：后续输出文本块
t_end：流式响应结束

TTFT = t1 - t0
E2E  ≈ t_end - t0
TPOT = (E2E - TTFT) / (实际输出token数 - 1)，仅对输出数 > 1
```

当前实现的 E2E 取流式响应处理末尾记录的时间，可能包含结束消息的少量开销，并非严格的最后一个 token GPU 完成时刻。

### 7.2 TTFT 从什么时候开始

不是“进入服务端 CPU 队列才开始”。本地 `bench_serving.py` 在 HTTP 请求发出前启动计时，因此一般包括网络、服务端排队、prefill、首 token 产生和返回。

如果启用客户端 semaphore，等待获得发送名额发生在请求函数外，通常不计入该请求 TTFT。用户真实感知若从点击/计划到达开始，还要把这段客户端等待算进去。

例子：

```text
客户端上限 2，同时计划发送 A、B、C。
A/B 先获得名额；C 等 3 秒才获得名额。
C 发出后 200ms 收到首 token：
  工具记录 TTFT ≈ 200ms
  从最初计划发送算的等待 ≈ 3200ms
```

多个请求各自记录自己的 t0/t1，之后对逐请求 TTFT 求均值、P95/P99；不是把所有请求共用一个起点。

### 7.3 TPOT 为什么除以输出数减一

首 token 已包含在 TTFT 里，剩下 L-1 个 token 对应首 token 到最后 token 的生成过程。不能直接除以全部 L。

TPOT 不包含首次输出之前的排队，但包含开始输出后的暂停、抢占、调度间隔和通信等待。TPOT 上涨不一定是计时错误，也不一定是某个 kernel 单独变慢。

当前 `mean_tpot` 是先算每个成功请求的 TPOT，再对请求取平均，不等于必然按 token 加权的平均 ITL。

### 7.4 ITL 还有流式分块的影响

理想 ITL 是相邻 token 的到达间隔；HTTP/SSE 实际可能一次返回多个 token。当前 vLLM Completions 分支记录非空文本块之间的间隔，因此并不保证每个间隔对应一个 token。

投机一次接受多个 token 时尤其要注意。不能把“收到一个 chunk”当作“一次 GPU decode step”。P99 TPOT 是逐请求平均生成耗时的尾部；P99 ITL 是输出间隔的尾部，二者含义不同。

## 8. 吞吐、实际并发与 goodput

### 8.1 吞吐分别是什么

| 指标 | 公式 | 解释 |
|---|---|---|
| req_tp | 成功完成请求数 / 测试时长 | 每秒完成多少请求 |
| out_tok_tp | 成功请求输出 token 总数 / 测试时长 | 服务级输出 token 吞吐 |
| in_tok_tp | 成功请求输入 token 总数 / 测试时长 | 输入工作量折算速率 |
| total_tok_tp | 输入与输出 token 总数 / 测试时长 | 混合工作量；不能把两种 token 当作相同成本 |

项目的 out_tok_tp 分母是整场测试时长，包含 prefill、排队和收尾影响，**不是纯 decode kernel 活跃时间下的 tok/s**。要测纯 decode 阶段效率，需另外定义观察窗口和执行计时。

输出长度完全一致且请求均成功时，`out_tok_tp ≈ req_tp × 每请求输出长度`。长度不同则不能直接比较 QPS 判断谁的 GPU 更快。

### 8.2 real_concurrency 是什么

当前代码：

```text
real_concurrency = 所有成功请求 E2E 秒数之和 / 整场测试秒数
                 = req_tp × 成功请求平均 E2E（秒）
```

它是成功请求在计时区间内的**平均在飞数**，不是“有效输出时间比例”，也不是 GPU batch 大小。

例子：10 条请求都从 0 秒持续到 2 秒，则 E2E 总和为 20 请求·秒，除以 2 秒得到 10。请求区间可以相互重叠，因此这个数可以大于 1。

这也可以理解为：对时间轴上“此刻有多少条成功请求尚未完成”的曲线积分，再除以总时间。全程包含完整请求生命周期时，这个等式来自统计定义；稳态 Little's Law 则用于解释长期平均到达率、驻留时间和在飞数之间的关系。

限制：只统计成功请求，会漏掉失败/超时请求占用的时间；客户端 semaphore 等待不在请求 E2E 内；服务端 waiting 请求仍在 E2E 内。因而不能用 real_concurrency 与 max-num-seqs 比较，直接推断 GPU 是否排队或饱和。

### 8.3 goodput 的两个口径

历史脚本叫作 goodput 的量是：

```text
throughput_ratio = req_tp / 配置的 request_rate
```

建议叫“完成吞吐与目标到达速率之比”。它没有筛选满足延迟要求的请求，而且受有限测试时长、客户端实际发送速率影响。

请求级 SLO goodput 可以定义为：

```text
满足指定 TTFT/TPOT 等 SLO 且成功的请求数 / 观察时间
单位：req/s
```

例：100 秒完成 200 条，只有 150 条同时达标：普通吞吐 2 req/s，SLO goodput 1.5 req/s，达标比例 75%。三者不同。

P99 TTFT 与 P99 TPOT 分别达标，不直接给出“同一请求同时满足两项条件”的数量。精确 goodput 需要逐请求记录。

## 9. SLO 和派生指标该怎么用

SLO 是服务等级目标，例如“P99 TTFT 不超过 2 秒”“P99 TPOT 不超过 50ms”。它来自业务体验要求或明确的测试标准，不是所有模型通用的物理常数。

负载增大后，排队、较长的执行轮次、通信及抢占会增加时间，因此可能超过 SLO。超过 SLO 不代表计算结果错误，而是响应体验不再满足目标。

| 历史派生指标 | 可用含义 | 必须注意 |
|---|---|---|
| `out_tok_tp / GPU数` | 每卡服务输出吞吐 | PD 应除实际总卡数；不能只除 D 的 TP |
| `mean_e2e / output_len` | 包含首 token 等待的每 token 端到端耗时 | 不是 TPOT；实际输出长短变化时不要直接用配置长度 |
| `req_tp / request_rate` | 与目标发压速率的吞吐比 | 小于 1 不足以证明过载 |
| `out_tok_tp / real_concurrency` | 平均在飞请求对应的输出速率 | 不是 GPU 槽位利用率；固定长度时近似 output_len / mean_e2e |
| 满足 SLO 的最大测得 req_tp | 已测点中体验合格的最高完成速率 | 还需验证队列稳定、负载一致及测试足够长 |
| 达标 case 数 / 全部 case 数 | 当前采样网格中有多少档通过 | 不是请求级成功率或 SLO goodput |

`analyze.py` 当前仅按 model name 分组，会混合不同输入输出档后取最大/最小值。因此它适合概览，不能把那一个最大值称为整个模型的通用容量。

更合理的分组至少包括：模型/精度、输入输出分布、TP/DP/PD、总 GPU 数、投机状态、关键调度配置和测试运行。

当前雷达图的轴可能分别来自不同 case，不对应一个可实际部署的共同工作点。用于展示时应保留这些限制。

## 10. 为什么 TTFT、TPOT 会上涨，P/D 会不会互相影响

### 10.1 影响因素

| 因素 | 可能影响 TTFT 的方式 | 可能影响 TPOT/ITL 的方式 |
|---|---|---|
| request-rate 增加 | 请求积压、prefill 等待 | 活跃 batch 增大，迭代耗时变长 |
| max-num-seqs 调大 | 可能减少名额等待，也可能加重竞争 | 可能提升吞吐，也可能增加每轮时间 |
| 输入更长 | prefill 更多；KV 传输更多 | decode attention 需读更长历史 KV |
| 输出更长 | 已有请求驻留更久，间接影响后续准入 | 单请求更多轮，KV 不断增长 |
| prefill chunk 大 | 可能更快做完 prefill | 插入较长计算，拉长 decode 间隔 |
| decode 请求多 | 占用调度预算，延后 prefill | batch/资源竞争及通信成本变化 |
| KV 空间不足 | 准入等待、重计算 | 暂停、抢占、恢复导致停顿 |
| prefix cache 命中 | 减少重复 prefill 计算 | 不等于 decode 无需读取命中的 KV |
| TP 通信、PD 搬运 | 通信与交接增加首 token 路径成本 | TP 每轮通信可能影响生成速度 |
| CPU/网络瓶颈 | 发包、解析、调度、返回延迟 | 提交不及时、流式缓冲造成停顿 |
| Graph/编译/预热 | 冷启动、首次路径成本 | 运行模式、launch 开销影响迭代 |

### 10.2 为什么可能先 TPOT 变差，之后 TTFT 暴涨

当更多请求可以加入执行时，batch 变大。即便输出总 tok/s 上升，每个请求也可能更久才能轮到一个新 token，TPOT 先变大。

继续加压，完成速率不足以消化到达，KV 或其他调度资源受限，后续请求等待时间增加，TTFT 进一步上涨。

这只是一种常见演化，不是固定顺序；prefill 很重、序列上限较低或已有 KV 压力时，TTFT 可以先恶化。

### 10.3 “没超过并发上限就没排队”为什么不对

上限只是一项约束。即使 running 只有 176、max-num-seqs 是 256，也可能因 KV blocks 耗尽而无法再接纳请求。即使没有长期 waiting，chunked prefill 请求也可能需要多轮才能完成首 token。

因此 TTFT/TPOT 暴涨不应首先归因于“把等待错误算进去了”。服务端等待本来就是用户体验的一部分；需要先区分正确的服务延迟与不属于指标口径的额外时间。

## 11. 有限请求数造成的吞吐曲线偏差

### 11.1 公式如何得到

假设共 N 条请求，近似匀速到达，速率为 rate，每条请求都固定耗时 E 秒，没有排队。测试从首条开始发到最后一条完成：

```text
发完请求约需 (N-1)/rate 秒
总时长约为 (N-1)/rate + E
req_tp ≈ N / ((N-1)/rate + E)

忽略 N 与 N-1 的差异：
req_tp ≈ N / (N/rate + E)
req_tp/rate ≈ 1 / (1 + rate × E / N)
```

这个模型是假设“服务能维持固定 E、不发生排队”，不是“服务器算得无限快”；E 本身仍然包含实际生成所需时间。

### 11.2 数字例子

N=100、E=25 秒：

| rate | 近似发压时长 N/rate | 含收尾的总时长 | req_tp | req_tp/rate |
|---:|---:|---:|---:|---:|
| 1 | 100s | 125s | 0.80 | 0.80 |
| 2 | 50s | 75s | 1.33 | 0.67 |
| 4 | 25s | 50s | 2.00 | 0.50 |

即便每条请求延迟一直不变，req_tp 也会呈现变缓趋势，比值也会下降。假设固定 E 始终成立，rate 越大，公式甚至趋于 N/E；这个极限来自有限 N 与收尾计时，不是硬件吞吐极限。

因此不能仅凭 `req_tp/rate < 0.85` 或曲线变平宣称测出了容量。

### 11.3 怎么处理

- 让持续发压时间明显长于典型 E2E；用更长时间和足够多请求覆盖稳定阶段。
- 同时记录实际发出请求的时间、完成时间及服务器队列时间序列。
- 区分整场含收尾吞吐、稳定窗口完成吞吐与窗口内 token 产出。
- 对尾延迟和候选拐点重复测试；100 条请求的 P99 几乎由极少数尾部样本决定。
- 500 条也不是通用保证；取决于 rate、E2E 和需要观察的稳定性。

`num-prompts > max-num-seqs` 既不是发现过载的必要条件，也不是充分条件。KV/算力/token 预算可能让更小请求数就发生等待；反之，请求很多但到达很慢，也不会过载。

## 12. 更合理的性能测试：两阶段加验证

本节是我们讨论后的推荐测法，**不等于历史脚本已经完整自动实现**。

### 12.1 阶段一：找合适的执行并发与服务配置

固定模型、精度、输入输出档、硬件和投机开关，扫描候选 `max-num-seqs`，例如 8/16/32/64/128。

用能持续保持目标在飞数 K 的闭环负载：完成一条立即补一条。可以利用压测工具的客户端并发限制配合无限到达速率和足够多请求，但应核对实际发送轨迹，保证它确实维持并发，且客户端不是瓶颈。

客户端 K 与服务端序列上限是两件事，应分别记录。要避免把大量客户端排队误当作 GPU 的并发能力。

观察 output tok/s、req/s、TTFT、TPOT/ITL、实际 running/token 数、KV 占用和抢占。目标是找到吞吐收益已变小、延迟还可接受的配置，不是找到能设置的最大整数。

例：上限 32→64，吞吐几乎不变而 TPOT 明显变差，通常优先保留较低上限或继续分析 KV/调度原因。

`pd_probe.py` 当前不是这种持续闭环：它一次发 K 条，等整批完成再进入下一档，完成后不补发。它是短批次爬坡探测，适合诊断线索，不是稳定并发容量的最终测量。

### 12.2 阶段二：固定配置，逐步增加到达 QPS

固定选好的 `max-num-seqs` 等服务配置，改变 `request-rate`。客户端并发限制应足够宽松，避免请求在客户端被隐式截流；同时监测实际发出速率是否跟得上计划。

主要判据：

| 观察项 | 要回答的问题 |
|---|---|
| P95/P99 TTFT | 首 token 体验是否超过目标？ |
| P95/P99 TPOT，必要时 ITL | 输出速度/停顿是否超过目标？ |
| 实际到达率与完成率 | 持续窗口内是否长期入多出少？ |
| waiting 队列随时间变化 | 是稳定波动，还是持续增长？ |
| 失败/超时率 | 服务是否已经无法正常承接请求？ |
| output tok/s、KV、抢占、设备状态 | 变化更可能来自哪里？ |

当前主 CSV 有 mean/median/P99 TTFT、TPOT，没有 P95 TTFT/TPOT。若采用 P95 SLO，需保存逐请求数据后补算，不能把 P99 列改个名字直接用。

教学示例（非本项目实测）：

| 实际到达 QPS | 稳定窗口完成 QPS | P95 TTFT | P95 TPOT | 队列 |
|---:|---:|---:|---:|---|
| 0.5 | 0.5 | 200ms | 20ms | 基本为空 |
| 1.0 | 1.0 | 300ms | 25ms | 无持续增长 |
| 1.5 | 1.5 | 800ms | 45ms | 波动但稳定 |
| 2.0 | 1.7 | 持续上涨 | 65ms | 持续增长 |

如果 SLO 是 P95 TTFT≤1s、P95 TPOT≤50ms、成功率≥99%，则 1.5 QPS 是已测通过档，2.0 失败，下一步在中间精扫。

**延迟变差不等于已经过载；还能跟上 QPS 也不等于体验达标。** 最终报告“指定负载与 SLO 下的最大可持续到达 QPS”，并同时给出服务吞吐。

### 12.3 阶段三：复核候选边界

- 对通过档和失败档重复测量，避免把一个随机波动点当作边界。
- 观察稳定窗口内队列是否持续上升；有限时间只能提供观察范围内的证据。
- 过载点测完应等队列排空或重置状态，避免污染下一档。
- 用同一资源预算和负载配置复测参考框架。

结果不只是“最大并发率与最大 QPS”。并发的单位是请求数，QPS 的单位是请求/秒；应输出合适的并发配置、吞吐—延迟曲线、SLO 容量和每卡效率。

### 12.4 原来的两个拐点怎么保留

`find_knee.py` 当前规则：

```text
容量候选：req_tp / request_rate 首次低于 0.85
延迟候选：mean_tpot 首次大于基线 × 1.8
基线：最低几个 rate 点（至多3个）中最小的 mean_tpot
```

这可以作为历史自动筛选规则，但不是普适容量判据。前者受有限测试偏差影响，后者受基线选择、随机波动与只看均值影响。未触发规则只说明规则未触发，不能直接保证容量高于最高测试 rate。

建议保留“粗扫定位区间→精扫→复测”的工作流，把容量判断改为持续到达/完成/排队分析，把服务可用性判断改为明确 SLO。容量边界与 SLO 边界没有固定先后顺序。

## 13. PD 分离与 MooncakeConnector

### 13.1 P 和 D 各做什么

Prefill 处理 prompt，形成各层 KV，并产生首个输出所需的结果；Decode 在已有 KV 上逐步生成后续 token。

PD 分离把两类工作放在不同服务实例/卡组，目的是分别配置资源、调度与性能目标，并减少阶段之间的干扰。两侧通常各自有完整模型的逻辑层结构，可以再做 TP；不是把前 12 层给 P、后 12 层给 D。

### 13.2 当前项目的调用链

```text
客户端 → proxy :8000
              ↓ 请求复制为 max_tokens=1、stream=false
          Prefill :8100（TP4，GPU0～3，kv_producer）
              ↓ 返回结果及 kv_transfer_params
          proxy 将 KV 交接元数据放入原始请求
              ↓
          Decode :8200（TP4，GPU4～7，kv_consumer）
              ↓ 流式返回
客户端 ← proxy

实际 KV 数据：通过 MooncakeConnector/传输引擎交接
```

proxy 经 HTTP 传的是请求与交接元数据，不是把整个 KV 张量序列化成 JSON 再发送。`kv_transfer_params` 中的远端实例、block 等信息用于连接器找到/接收对应缓存。

配置指定 `MooncakeConnector`、producer/consumer，以及 RDMA 或 TCP 协议。MooncakeConnector 是框架 KV 传输接口到传输实现之间的适配，不等于完整 HTTP 路由系统，也不能与 LMCache 的缓存层混为一谈。

当前 proxy 支持实例列表轮询，但启动脚本实际配置一个 P 端点和一个 D 端点；这是 **1P+1D 实例，P/D 各 TP4，总共 8 卡**。

### 13.3 一般多少 P、多少 D

没有固定比例。取决于输入/输出长度分布、目标 SLO、各阶段每实例吞吐、TP 大小、KV 传输带宽和缓存容量。

可先用同一工作负载下的阶段容量估算：若目标是 λ req/s，一个 P 实例可持续处理 μP req/s，一个 D 实例可持续处理 μD req/s，则实例数至少分别按 λ/μP、λ/μD 估计，再留余量并实测。

这个估算里的 μ 必须已经包含实际长度分布和部署配置，不能直接拿不同场景的 tok/s 当作同一种容量。

### 13.4 为什么做 PD 分离：减少阶段干扰，分别配置资源

集中式服务把 prefill 和 decode 放在同一模型实例中。它们可以出现在同一次混合调度，也可能按不同轮次交错执行，共享 GPU、KV 池和调度预算。

- 长 prefill 占用较长执行时间，可能让正在输出的请求等待，增加 ITL/TPOT。
- 如果调度更偏向保护 decode，prefill 可能被切成多个 chunk、分多轮完成，增加新请求 TTFT。
- Chunked prefill 可以缓和矛盾，但不会凭空增加硬件资源，也不能保证消除所有干扰。

PD 分离把两个阶段放到不同实例，使它们可以分别选择 batch/token 预算、TP 大小、实例数量和优化路径。主要价值是隔离干扰、控制尾延迟，并争取提高满足指定 SLO 的可用吞吐；不是保证裸吞吐一定提高。[vLLM PD 说明](https://docs.vllm.ai/en/latest/features/disagg_prefill/)、[DistServe 论文](https://arxiv.org/abs/2401.09670)

这种隔离也不是绝对的：P/D 仍可能共享网络、CPU 或互联，而且 D 要等待请求交接和所需 KV。收益需抵消 KV 传输、协调开销、两侧模型驻留和资源配比不均等成本。

不能把“prefill 常偏计算、decode 常偏访存”当作所有负载的固定属性。小 batch decode 的线性层往往权重带宽占比高；batch 增大后权重复用改善，GEMM 可能转向计算受限。Attention 的历史 KV 读取则有不同的成本结构。

### 13.5 增加 D 实例与 DP 是什么关系

推理 DP 的基本含义是：多个完整的逻辑模型副本分别处理不同请求。一个副本可以在单卡上，也可以由多张卡通过 TP 共同承载。

```text
一个 D 实例，TP4：
  GPU0～3 共同处理这一实例接收的请求

两个 D 实例，每个 TP4：
  D0：GPU0～3，处理请求组 A
  D1：GPU4～7，处理请求组 B
  共 8 张 D 卡，由路由器分配请求
```

因此，增加 D 副本属于推理副本扩展/DP 思路；不是让两组副本一起计算同一个 token。两组副本内部各自的 TP 卡才是在共同计算同一批请求。

多个独立启动的同模型服务配合外部负载均衡，也可以形成这种部署。它不一定通过 `--data-parallel-size` 启动，框架内部 DP 的支持方式要看版本和模型。训练 DP 需要梯度同步；推理副本通常没有这一步，但路由、控制面和缓存传输仍可能通信。[vLLM DP 部署说明](https://docs.vllm.ai/en/v0.20.0/serving/data_parallel_deployment/)

项目当前实际是 1P+1D，各 TP4；上面的多 D 副本是扩展思路，不是本项目已经验证的部署结果。扩展 D 后还要重新检查 P 容量、KV 传输、负载均衡和总 GPU 成本。

## 14. PD 各阶段的优化与 layerwise

### 14.1 优化手段按瓶颈选择

| 位置 | 可能使用的手段 | 要验证的代价/前提 |
|---|---|---|
| Prefill | 高效 attention/FlashAttention、合适的 GEMM/低精度路径、prefix reuse、合理 batching/chunking、TP 或上下文并行 | kernel 支持、数值质量、通信和 TTFT |
| Decode | 权重量化、高效小批矩阵算子/paged attention、合理 continuous batching、Graph、KV 精度/布局优化、投机 | 是否带宽/launch/计算受限，KV 压力与接受率 |
| KV 传输 | RDMA、注册内存复用、异步传输、合理分块、layerwise、减少冗余数据 | 总字节数、带宽、布局兼容、同步依赖 |
| 系统调度 | 调整 P/D 比例、路由和准入策略，控制队列，分别优化 SLO | 资源成本、负载变化、故障恢复 |

量化不是只对 decode 有用，FlashAttention 也不是 PD 才有的技术。不同阶段的收益大小由具体工作负载和实现决定。

### 14.2 layerwise 是什么

按 Transformer 层组织 KV 的发送/接收，把通信与其他层的计算重叠：

```text
P：第1层产生KV → 发送第1层KV
P：计算第2层   ↔ 前一层KV传输
P：计算第3层   ↔ 第二层KV传输
...
```

收益主要是缩短“全部计算完以后还要整块传一次”的尾部等待。通常并不减少 KV 总字节数，也不直接减少 D 的矩阵运算量；分块太细还可能增加启动开销。

D 计算某一层时需要该层的历史 KV，不必在数学上等所有层 KV 才能计算第一层。但真实系统还要满足输入 token 已确定、请求已交接、连接器可用等条件。

特别是第一个生成 token 常需 P 完成全部层和 LM Head 后才确定，不能据此声称 P 刚算完第一层 D 就必然开始整个首轮 decode。本项目 proxy 代码先等待 P 的 HTTP 响应，再提交 D，更不能直接宣称已实现 P/D 前向全程流水。

LMCache 的 layerwise 接口可见 `wait_for_layer_load`、`save_kv_layer`；本地可继续看 [LMCache/vLLM-MUSA 可行性记录](../mthreads/my_vllm_test/vllm_020/lmcache_on_vllm_musa_020_feasibility.md)。框架存在这些 hook，不等于本次 Mooncake PD 已启用按层重叠。需要核对连接器实现、配置和 timeline。[LMCache layerwise 文档](https://docs.lmcache.ai/kv_cache_optimizations/layerwise.html)

### 14.3 D 侧四个常用调优方向

| 方向 | 实际调整什么 | 主要权衡 |
|---|---|---|
| 活跃请求数 | `max-num-seqs` 等调度约束，结合实际 running/scheduled tokens | batch 增大可能提升总吞吐，但单轮更慢、每请求 TPOT 变差；配置上限不等于实际 batch |
| KV 容量 | KV 精度、显存预算、上下文长度、缓存管理，以及适用的并行分担 | 容纳更多请求、减少抢占；有空间不代表读取这些历史 KV 没有带宽成本 |
| 并行策略 | TP/PP，以及支持条件下的 DCP 等 | 分担权重、计算或 KV，同时引入通信、同步和调度代价 |
| 实例数 | 增加独立 D 副本并分流请求 | 增加总容量、降低每副本负载，但增加模型驻留、GPU 和路由成本 |

举例：batch=16 时每轮 10ms，约输出 1600 tok/s；batch=32 时每轮 18ms，约输出 1778 tok/s。总吞吐提高，但每请求的生成间隔变长。这是普通每请求每轮生成一个 token 的教学示例，不是项目实测，也不直接适用于投机解码。

### 14.4 KV 充足但 TPOT 高：batch、kernel 和通信分别看什么

**看 batch：** 核对实际调度序列数、执行 token 数和每轮时间。batch 大时，每轮工作量增加；线性层可能因权重复用提高而更偏计算受限，但 TPOT 上升并不要求 GPU 已经变成计算瓶颈。Attention 对不同请求的 KV 通常不能像模型权重那样直接共享复用。

**看 kernel：** 不是只数 kernel 数量，也不是把 kernel 数量当作计算量。

- 先看时间线：GPU 是否有明显空隙，CPU 提交、同步或依赖等待是否位于关键路径。
- 再按算子/阶段汇总耗时，定位线性层、attention、归一化、缓存操作等主要成本。
- 对慢 kernel 进一步检查形状适配、访存效率、有效带宽、计算单元利用、占用率，以及实际是否走预期的 Tensor Core/低精度路径。
- kernel 很多且很短时，launch 开销可能明显；kernel 少但每个都很慢，也可能是带宽、计算或实现效率问题。

exllamav2 项目中比较小 M 下 `at::mm` 与直接 `mublasHgemm` 的思路可作为例子：数学任务相近，实际路由和形状适配不同，耗时仍可能相差很大。不能仅凭“都是一次矩阵乘”判断性能相同。

**看通信：** TP 的层内归约会反复出现在每轮 decode 中，可能直接拉长 TPOT；PD 的 KV 交接主要发生在阶段切换处，常影响 TTFT/交接延迟，但共享互联争用也可能间接影响正在运行的请求。应检查传输量、拓扑、有效带宽和重叠情况。

通信算子时间长还可能包含等待其他 rank 到达的时间，因此需区分链路慢和计算/调度不均导致的等待，不能全部算成网络传输成本。

### 14.5 TP 与 PD 的通信不是同一条链

```text
P 实例内部：TP 各卡共同计算 prefill，层内交换/合并结果
       ↓
P → D：交接该请求所需的各层 KV 与元数据
       ↓
D 实例内部：TP 各卡共同计算 decode，每轮再次进行层内通信
```

Layerwise 优化的是按层组织 KV 交接、隐藏传输等待；TP 的 All-Reduce 则用于合并同一层计算的部分结果。两者作用不同，不能把“按层传 KV”理解为替代 TP 归约。

## 15. PD 实验结果：能说什么，不能说什么

### 15.1 历史记录的观察

Qwen3-32B，3.5k/1k、rate=1.0 的某次 PD 观察中记录：

- D 侧设备利用率约 99%～100%。
- P 侧平均约 21%，P waiting 为 0。
- D 的 KV cache 占用到达 100%，随后等待队列增长，峰值约 64。
- 某次监控 running 峰值约 176，低于 max-num-seqs=256。

这些数据支持“当时 D 侧存在明显压力，KV 容量限制了继续接纳请求，不能只靠提高序列上限解决”。它们不直接证明 D 是算力瓶颈，因为设备利用率高不等于计算单元吞吐已满；访存、通信以及其他 kernel 活动也可能使设备保持忙碌。

KV 满与等待增长的时间相关性，是定位线索；仍应检查具体 KV 分配、抢占与调度事件，不把单条时间序列当作完整因果证明。

### 15.2 “PD 比集中式低约 15%”应怎样说

记录列出集中式约 0.95 req/s、PD 约 0.81 req/s：按这两点计算，后者低约 15%。这首先是特定测试条件下的完成吞吐差，不能未经验证就升级为稳定容量差或纯 decode kernel 差。

比较资源：集中式 TP4 使用 4 卡；1P-TP4 + 1D-TP4 使用 8 卡，但 D 侧仍只有 4 卡。如果工作负载主要受 D 限制，额外 P 卡未必提高吞吐，还增加交接成本。

这解释了为什么“多了 P 卡也不一定赢”，但不足以精确解释全部 15%。P 平均利用率低也不等于毫无价值，它可能提供隔离或突发处理能力。

公平比较最好同时报告：

- 相同 D 资源时，增加 P 资源后的收益和成本。
- 相同总 GPU 预算时，PD 与两个 TP4 集中式副本等方案的对比。
- 相同 SLO 下的请求吞吐和每卡输出吞吐。

不能把“prefill 填补 decode 内存带宽空隙”当作已证实解释。若 decode 本来带宽受限，带宽未必有空隙；混合批处理可能改善计算资源利用或权重复用，也可能造成干扰，需要实际剖析。

PD 的价值也不能简化为“只适合长输入短输出”。请求分布、隔离需求、通信成本、资源配比都会影响结果。

### 15.3 EAGLE3 开关对照的原始记录

| 指标 | 无投机 | 开 EAGLE3 |
|---|---:|---:|
| req_tp | 0.71 | 0.70 |
| mean TTFT | 48s | 80s |

可以说“该负载下没有观察到吞吐收益，TTFT 更高”。不能凭单次 0.71→0.70 就证明显著吞吐下降，更不能推广成“投机对容量始终无效”。

### 15.4 pd_probe 的两个测量限制

它先单独测 P 的一次短批次，再测 proxy 的另一批请求，使用 `proxy TTFT - prefill耗时` 作为残差。这个差包含两组实验的排队、缓存、请求路径和负载差异，不能直接等同 Mooncake 传输时间。

它还把 SSE `data:` 消息数量近似当 token 数，并用首个 data 消息作为首响应。投机合并输出、元数据消息等都会影响计数，因此输出的 TPOT 只是粗略诊断值。精确测量需要解析有效文本及实际 token 数，最好复用正式 benchmark 的口径并继续核验 chunk 问题。

“改发送线程数后没改善，所以必定是 proxy”也不成立；KV 准入、D 排队、其他通信同步等都可能进入残差。

## 16. EAGLE3：算法、接受率与为何不一定加速

### 16.1 它怎么提出候选

EAGLE3 使用针对目标模型训练的小草稿网络。目标模型一次正常前向产生低/中/高层特征，拼接后投影融合，再结合已知的下一个 token embedding，预测后续 token。继续草拟时使用自己的输出特征递推，而不是每次重新跑目标模型，也不是直接拿目标模型 KV 当预测器。训练会覆盖这种自回归使用自身特征的情形。[EAGLE3 论文](https://arxiv.org/html/2503.01840v1)

官方代码中，融合特征与 token embedding 分别归一化后拼接，交给草稿 attention 的 Q/K/V 投影；不能强行把示意图理解成代码必有一个独立的 `2H→H` FC。草稿也有自己的 attention cache 和输出头。[EAGLE 官方实现](https://github.com/SafeAILab/EAGLE/blob/main/eagle/model/cnets.py)

### 16.2 用 Qwen2.5-0.5B 举例（讲解示例，不是本项目已部署项）

该模型 24 层、H=896、14 个 Q head、2 个 KV head、head dim=64、词表 151936。[Qwen 配置](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct/blob/main/config.json)

假设有配套训练好的 EAGLE3、草稿 H 也为 896，每轮提出 3 个 token，使用贪心解码，先只看一条候选链：

```text
prompt=[x1,x2,x3,x4]
  → Qwen 正常 prefill，hidden [1,4,896]
  → 最终 Norm + LM Head，最后位置预测出 y1
  → 目标 KV 此时只有 prompt，尚没有 y1

三层特征：[1,4,896] × 3
  → 拼接 [1,4,2688] → 线性融合 [1,4,896]，记作 g

草稿初始化使用移位对齐：
特征：g1  g2  g3  g4
token：x2  x3  x4  y1

最后位置：g4 + embedding(y1) → 小网络特征 a1 → 候选 A
下一步：  a1 + embedding(A)  → 小网络特征 a2 → 候选 B
下一步：  a2 + embedding(B)  → 小网络特征 a3 → 候选 C
```

验证时，目标模型输入 `[y1,A,B,C]`，在缓存 prompt 上一次执行 4 个位置，仍然顺序经过完整 24 层。最后 logits 的逻辑形状为 `[1,4,151936]`。

| 输入位置 | 该位置输出用于预测/验证 |
|---|---|
| y1 | A 是否正确 |
| A | B 是否正确 |
| B | C 是否正确 |
| C | 若前三个都接受，可再给出一个 token |

这些位置能并行验证，是因为候选已经给定；因果 mask 仍然存在，并没有让模型看到未来正确答案。

若 A、B 对，C 应为 D：接受 A/B，采用目标给出的 D；保留 prompt/y1/A/B 的目标 KV，舍弃 C 的 KV，D 尚未经过目标前向，作为下一轮根 token。

若 A 就错了，B/C 的条件上下文已经不对，整条后续候选链都要舍弃；但目标仍输出正确替代 token，因此该轮推进 1 个 token，而不是 0。

树状草稿可保留另一条匹配分支；单链示例只是便于理解，不代表所有 EAGLE3 部署都只生成一条链。随机采样也不能简单用逐位置 argmax 匹配代替接受/修正规则。

### 16.3 接受率与平均接受长度

vLLM 的参考指标代码：

```text
接受率 = accepted draft tokens / proposed draft tokens
平均接受长度 = 1 + accepted draft tokens / draft rounds
```

后一项按惯例包括目标模型额外给出的 token。若每轮固定提出 3 个：

```text
61%：   平均接受长度 ≈ 1 + 3×0.61  = 2.83，约为记录中的2.84
18.8%： 平均接受长度 ≈ 1 + 3×0.188 = 1.564，约为1.57
```

因此“平均接受长度 1.57”不是“接受了 1.57 个草稿”，而是平均约 0.57 个草稿加 1 个目标 token。

逐位置 0.80/0.61/0.42 表示该位置被接受的轮次比例，包含前面位置也通过的条件；不是三个独立的条件接受率。它们的和约为每轮接受草稿数。日志按时间窗口汇总后重置，不能默认某条日志代表整场测试。[vLLM 0.20.0 指标代码](https://github.com/vllm-project/vllm/blob/v0.20.0/vllm/v1/spec_decode/metrics.py)

### 16.4 61%→18.8% 能不能解释为过载导致

不能直接这样解释。原记录未标清两组数字分别来自哪个运行、rate、时间窗口，不能断言 61% 是未过载基线。它也不可能是“未开启投机时的接受率”。

相同上下文、权重、采样规则和数值结果下，排队更久不会让模型猜错。TTFT 是时间指标，不是决定草稿准确率的输入。

需排查：日志窗口中的请求/生成位置是否不同，目标/draft/量化/采样配置是否一致，batch 改变是否切换数值路径，以及接受统计口径是否一致。数值变化是可能因素，不是已证明的根因。

验证办法：固定输入集合、输出长度、模型/draft、采样参数和候选数，只改变发压速率，记录整场计数及分窗口/分请求统计，再定位差异。

### 16.5 为什么开了可能更慢

可用粗略成本模型理解：

```text
投机平均每个有效输出 token 的成本
≈（草稿成本 + 目标批量验证成本 + 管理成本）/ 平均推进长度
```

候选接受多时，用较少的目标模型串行轮次推进更多 token，可能提高权重复用、降低延迟；接受少、验证变贵或额外调度负担大时，收益被抵消。

大 batch 下目标模型原本已经较好地复用权重，投机的额外计算可能不划算。但不能推导出“所有高负载必然变慢”，更不能把拒绝的 token 数直接换算为同等比例的 GPU 算力浪费。[vLLM 投机说明](https://docs.vllm.ai/en/latest/features/speculative_decoding/)

Qwen2.5-0.5B 本身较小，草稿和输出头开销占比可能较高，也不保证有收益。该例用于解释算法，不替代实际 benchmark。

## 17. 跨框架公平比较与监控

### 17.1 vLLM 与 SGLang 怎么讲

两者都是推理服务框架，会在调度、前缀缓存、attention backend、低精度 kernel、Graph、投机和分布式实现上存在版本相关差异。

vLLM 的 PagedAttention/KV block 管理、SGLang 的 RadixAttention/前缀复用可作为理解入口，但不能说“只有 SGLang 有前缀缓存”或“只有 vLLM 有 continuous batching”。本项目应讲具体版本和路径，不给框架贴永远快/慢的标签。

PagedAttention 的重点是 KV 按逻辑 token block 管理，通过 block table 映射到物理缓存块，使请求不必获得整段连续 KV 显存，并配合 attention kernel 读取。Prefix caching 则复用已经计算的相同前缀 KV，两者相关但不是同一个概念。

### 17.2 必须对齐和记录的条件

| 类别 | 条件 |
|---|---|
| 模型 | checkpoint/revision、tokenizer/chat template、权重和 KV 精度 |
| 硬件 | GPU 型号/总数、TP/DP/PP、互联、CPU/NUMA、功耗/时钟状态 |
| 软件 | 镜像、包版本/commit、驱动、MUSA/torch_musa、attention backend |
| 工作负载 | 相同请求集合、长度分布、输出终止规则、随机种子、前缀重复比例 |
| 发压 | 目标及实际到达速率、间隔分布、客户端限制、总时长、流式设置 |
| 优化 | prefix cache、chunked prefill、Graph、投机/draft/候选数 |
| 统计 | 预热、首尾是否计入、成功/失败口径、实际 token 数、分位数、重复次数 |

可以做两种不同问题的对比：统一资源和关键配置的基线比较；相同资源预算和 SLO 下分别调优后的最佳配置比较。二者都合理，但应明确目的，不能悄悄混用。

不同系统为了定位各自边界，可以扫描不同 rate 网格；若比较同一负载下延迟，则必须有共同的实际到达速率及相同到达分布。

### 17.3 /metrics 看什么

vLLM 的 `/metrics` 是服务暴露的 Prometheus 格式监控接口，提供运行/等待请求、KV 使用等时间序列。它与客户端 CSV 互补，不是自动帮忙解释原因的 profiler。

本项目 `pd_monitor.py` 读取 P/D 的 running、waiting、KV cache 使用率，并采集设备利用率。指标名可能随版本改变，所以脚本对 KV 指标做了多个名字的兼容。

`mthreads-gmi` 中显存占用很高，可能只是引擎提前预留了 KV 池；不等于池内 token blocks 已全部使用。应结合 KV cache 使用指标。

设备 util 高也不等于计算密集。若要归因 kernel、显存带宽、TP 通信或 CPU launch，需要进一步采集 timeline 和相应硬件计数器。

### 17.4 并行策略简表

| 策略 | 切分对象 | 与本项目的关系 |
|---|---|---|
| TP | 单层张量/权重，跨卡共同完成同一请求的层计算 | TP4 是实际部署方式，会有层内通信 |
| DP | 完整模型副本，各自处理不同请求 | 同模型多个副本时可用于总容量扩展；8个不同模型不是一个模型的DP |
| PP | 不同层放不同卡/阶段 | 当前命令 PP=1 |
| CP | 长上下文/token 维度上的计算或 KV 分担 | 原理补充，不属于已验证的本项目部署 |
| PCP/DCP | 分别面向 prefill/decode 的上下文并行实现 | 支持方式、通信和与TP组合取决于框架版本，不与PD混为一谈 |
| PD | 不同服务实例承担不同生成阶段 | 当前扩展为1P-TP4+1D-TP4 |

推理 DP 中，不同请求通常不需要像训练那样同步梯度，但路由、控制面、共享缓存等仍可能通信。不能说所有 DP 系统一点交互都没有。

### 17.5 vLLM 的 TP：配置卡数，模型实现决定切分方式

用户一般通过 `--tensor-parallel-size 4` 指定 TP 大小，模型代码决定哪些线性层使用列并行、哪些使用行并行。并不是再选一个“全模型统一按行切/按列切”的启动开关。[vLLM 并行部署文档](https://docs.vllm.ai/en/v0.20.1/serving/parallelism_scaling/)

以下按普通稠密 Transformer TP 前向解释，不叠加 PP、CP、sequence parallel 或特殊通信融合。采用数学记号：

```text
Y = X @ W
X：[T, K]，W：[K, N]，Y：[T, N]
T：本轮参与计算的 token 数
K：输入特征维度，也是矩阵乘的累加维度
N：输出特征维度
```

这里的行/列指上述逻辑 W 的维度。PyTorch Linear 通常将权重存成 `[out_features, in_features]`，所以不能根据物理张量的行列直接套用名称；这也与 row-major/column-major 内存布局不是一回事。

| 切分方式 | 切分逻辑 W | 每卡的计算结果 | 恢复完整输出的操作 |
|---|---|---|---|
| Column Parallel，列并行 | 按 N，输出特征切分 | 一部分输出通道的完整值 | 沿输出维度拼接；后续能消费分片时可暂不拼接 |
| Row Parallel，行并行 | 按 K，输入/累加维度切分 | 所有输出通道的部分和 | 对应元素求和 |

两卡的数学例子：

```text
列并行：W = [W0, W1]
  GPU0：Y0 = X @ W0
  GPU1：Y1 = X @ W1
  Y = concat(Y0, Y1)，不是 Y0 + Y1

行并行：W 沿 K 分为 W0、W1，X 同样沿 K 分为 X0、X1
  GPU0：P0 = X0 @ W0
  GPU1：P1 = X1 @ W1
  Y = P0 + P1，P0/P1 的形状都与 Y 相同
```

列并行各卡算的是不同输出位置；行并行各卡算的是同一输出位置所需的不同累加项。vLLM 对应的核心类是 `ColumnParallelLinear` 和 `RowParallelLinear`。[vLLM Linear 源码](https://github.com/vllm-project/vllm/blob/v0.20.1/vllm/model_executor/layers/linear.py)

### 17.6 MLP：列并行与行并行配对，中间不用收集完整激活

用 TP2、输入维度 H=8、中间维度 I=16 举例。以下省略 bias：

```text
g = X @ W_gate
u = X @ W_up
z = SiLU(g) * u
Y = z @ W_down

                      两卡都有 X：[T, 8]
                         /          \
                       GPU0         GPU1
gate/up 列并行：       中间通道0～7  中间通道8～15
本地逐元素运算：       SiLU(g0)*u0   SiLU(g1)*u1
得到分片：             z0：[T,8]     z1：[T,8]
down 行并行权重：      Wd0：[8,8]    Wd1：[8,8]
本地矩阵乘：           P0：[T,8]     P1：[T,8]
                         \          /
                       All-Reduce 求和
                          Y = P0 + P1
                      两卡都得到完整 [T,8]
```

关键是每张卡拥有相互对应的 gate/up 通道，SiLU 和逐元素乘法可以本地完成；down 的输入维度又按同样的通道切分。因此，**up 与 down 之间不必先 All-Gather 完整中间激活，down 之后才合并部分和。**

这不是为了少通信而省略必要计算，而是切分配对使中间计算在数学上就不需要跨卡数据。

上游 vLLM 0.20.1 的 Qwen2 MLP 使用 `MergedColumnParallelLinear` 合并 gate/up 投影，down 使用 `RowParallelLinear`。Attention 则使用 `QKVParallelLinear` 和行并行的 O 投影。这里用于解释实现结构，不代表已经核验本地 MUSA 分支的所有改动。[Qwen2 源码](https://github.com/vllm-project/vllm/blob/v0.20.1/vllm/model_executor/models/qwen2.py)

### 17.7 Attention 和整个 Transformer layer 的通信位置

普通按 head 切分的 Attention TP 中，各卡先得到自己负责的 Q/K/V head，完成这些 head 的 attention，再经 O 投影计算对完整 hidden 输出的部分贡献。若 GQA 的 KV head 数少于 TP 卡数，一部分 KV head 会跨卡复制，不能认为 Q/K/V 总是全部均匀除以 TP。

```text
一个 Transformer layer 的主要前向链：

输入 / RMSNorm
  ↓
QKV 投影：列并行，分配 heads
  ↓
本地 RoPE、KV cache 操作、attention
  ↓
O 投影：行并行
  ↓
All-Reduce                         ← Attention 子模块结果合并
  ↓
残差、RMSNorm
  ↓
gate/up 投影：列并行
  ↓
本地 SiLU(gate) × up
  ↓
down 投影：行并行
  ↓
All-Reduce                         ← MLP 子模块结果合并
  ↓
残差及下一层
```

这是逻辑顺序，实际 residual/norm 可融合或延后到下一次调用。因此通常说每个 Transformer block 有两处主要的 TP 归约，而不是只在整个 block 结束后通信一次，也不是每个 Linear 后都通信。

行并行后的 All-Reduce 让各卡都持有完整输出，可以继续进入下一组列并行；无需每一层都先从某一张卡重新广播完整 hidden states。TP 权重通常在加载时分片驻留，也不是每轮 decode 都把全部权重 All-Gather 回来。

上图不是所有实现的通信总表。Embedding/LM Head、特殊模型结构，以及 sequence parallel、通信融合等都可能增加或改变通信位置。

### 17.8 Reduce-Scatter、All-Gather、All-Reduce 到底有什么区别

先区分“最终得到什么结果”和“底层怎样传输”。以下 reduction 使用逐元素求和：

| 操作 | 最终各卡持有什么 |
|---|---|
| Reduce | 只有指定 root 得到完整求和结果 |
| All-Reduce | 每张卡都有完整求和结果 |
| Reduce-Scatter | 每张卡持有求和结果的一片；每片已经包含所有参与卡的贡献 |
| All-Gather | 每张卡都得到所有输入片段的拼接结果，不做求和 |

```text
初始：
  GPU0：[1,  2,  3,  4]
  GPU1：[10, 20, 30, 40]

Reduce-Scatter 后：
  GPU0：[11, 22]
  GPU1：[33, 44]

再执行 All-Gather：
  GPU0：[11, 22, 33, 44]
  GPU1：[11, 22, 33, 44]
```

**在相同通信组、匹配分片布局和对应归约规则下，Reduce-Scatter 后接 All-Gather，从结果上等价于 All-Reduce。**

“先归约，再分片”描述数学语义，不要求真的先在某张卡生成完整和再分发。Ring Reduce-Scatter 可以边传递边求和，最后各卡得到已经求和完成的一片；再 All-Gather 这些片段，才让每卡拥有全份。不能仅凭“边传边求和”就判断是完整 All-Reduce。[NCCL 集合通信说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)

这些操作独立存在的意义是：如果后续计算只需要本卡负责的结果片段，就可以停在 Reduce-Scatter，保持激活分片；需要完整输入时再 Gather。sequence parallel 等方案会利用这种安排，但不能把它当作当前普通 TP 配置必然开启的行为。

### 17.9 Ring 是算法，All-Reduce 是操作；不能从 TP 参数猜出后端

经典 Ring All-Reduce 分成两个阶段：

```text
Reduce-Scatter：沿环传递并归约，各卡得到最终结果的一片
      ↓
All-Gather：沿环交换这些片段，各卡得到完整结果
```

框架代码可能只调用一次 `all_reduce()`，由通信实现内部完成这两阶段，不一定显式调用两个独立 API。

All-Reduce 不一定使用 ring；通信库可根据消息大小、硬件拓扑等选择 ring、tree 或其他实现。NCCL 也提供算法相关配置，因此不能把所有 TP 通信都称为“ring-gather”。[NCCL 算法配置](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html#nccl-algo)

本项目是 MUSA 环境。是否使用 MCCL、框架自定义归约或其他适配路径，以及底层算法是什么，需要读取该版本实现、运行日志或 profiler；不能从上游 NVIDIA 路径或 `--tensor-parallel-size 4` 直接推断。

面试可表述为：

> TP 通常把 QKV、gate/up 做列并行，把 O、down 做行并行，让中间激活保持分片并在本地计算，最后归约部分和。普通 Transformer block 通常在 Attention 输出和 MLP 输出各有一处主要 All-Reduce。Ring 是 All-Reduce 的一种实现方式，经典实现由 Reduce-Scatter 和 All-Gather 组成；本项目实际通信后端和算法需要依据 MUSA 版本与 trace 确认。

### 17.10 TP、PP、推理 DP 应怎样放在服务器上

普通稠密模型推理中，通常优先把同一 TP 组放在高速互联的 GPU 范围内，例如同机 NVLink/NVSwitch 卡组；PP 阶段和不同推理副本可以跨服务器。

| 方式 | 主要通信 | 部署倾向与限制 |
|---|---|---|
| TP | 每层反复合并部分计算结果 | 对带宽和延迟都敏感，优先高速互联；不是绝对不能跨机 |
| PP | 相邻阶段之间传递激活 | 可以跨机，但有阶段依赖、流水空泡和负载不均 |
| 推理 DP/副本 | 不同副本独立处理请求，通常不交换逐层结果 | 适合跨机扩容量；仍有路由、控制面等成本 |

例如两台各8卡服务器：一个大模型可用每机TP8、跨机PP2；若完整模型单机能放下，也可每机各起一个TP8副本处理不同请求。前者共同完成一个模型副本的前向，后者是两个独立副本。

“同机”只是常见经验，最终要看实际互联、GPU映射和后端；同机PCIe卡组不等于NVSwitch卡组。训练DP另有梯度通信，不能套用推理副本的低交互假设。[vLLM 多机部署建议](https://docs.vllm.ai/en/v0.21.0/serving/parallelism_scaling/)

### 17.11 TP 的计算收益与通信成本如何权衡

可以用关键路径上的简化时间模型理解：

```text
一次模型执行时间
≈ 本地计算与访存时间
 + 未被计算隐藏的通信时间
 + 调度及其他开销

增大TP有利于降低执行延迟的条件：
本地执行节省的时间 > 新增通信、同步及其他开销
```

不能把所有rank上通信kernel的持续时间相加，直接当作请求的通信成本：通信可能重叠，也可能包含等待慢rank到达的时间。需看时间线与依赖关键路径。

TP变大后，收益可能递减：

- 每卡GEMM变小，计算量下降却未必等比例提速，可能降低Tensor Core利用率。
- launch、部分归一化、调度和复制的状态不会严格除以TP。
- O/down投影后通常仍要归约完整hidden输出的部分和；单次张量逻辑形状约为 `[本轮token数, hidden_size]`，不会因为TP翻倍就简单缩小为一半。
- rank更多、拓扑变化或跨机，可能增加集合通信和同步成本。通信时间取决于具体算法，并非必定线性随TP增长。

下面仅是教学数字，省略其他固定开销，不是项目实测：

| 配置 | 本地执行 | 未隐藏的通信 | 总时间 |
|---|---:|---:|---:|
| TP1 | 20ms | 0ms | 20ms |
| TP2 | 11ms | 2ms | 13ms |
| TP4 | 7ms | 4ms | 11ms |
| TP8 | 5ms | 8ms | 13ms |

这里TP4→TP8仅省2ms本地执行，却多4ms通信，因此变慢。实际情况必须测量，且只能比较模型支持的合法TP配置。

**不同负载需要分别看：** 长prefill有较大GEMM可分担，但激活通信量也较大；小batch decode常受权重读取、短kernel和小消息延迟影响；大batch decode权重复用提高，同时每轮计算量、KV读取和通信量也变化。不能说“decode访存密集，所以TP没用”：多卡可以分担权重读取，利用多张卡的带宽，只是收益可能被通信抵消。

通信与计算重叠也不是任意的：当前层需要的归约未完成，依赖其完整输出的下一步不能直接消费结果。分块流水、融合或多批次交错能否隐藏通信，需要实现与数据依赖共同支持。

优化本地kernel后通信占比变大，不等于优化失败。可能本地耗时已下降、总时间更短，只是通信成为下一步瓶颈；应比较绝对时间和最终服务指标。[NVIDIA 对 TP 激活通信的说明](https://docs.nvidia.com/deeplearning/transformer-engine/examples/advanced_optimizations.html)

### 17.12 “按 N 切”必须说明是哪一个 GEMM；TP 不能任意增加

此前列并行中的N，指线性投影的输出特征维度：

```text
Q投影：X[T,hidden] @ Wq[hidden,Hq*D] → Q[T,Hq*D]
                             ↑ 输出N，通常按完整head分组切

单head的decode attention：Q[1,D] @ Key^T[D,S] → score[1,S]
                                                        ↑ 这里的N是历史长度S
```

普通head TP切的是heads，并不因为第二个矩阵乘的N=S，就自动把历史序列分给不同卡。QKV投影、QK乘法和PV乘法的M/N/K必须分别理解。

以已经核对的上游vLLM 0.20.1 Qwen2实现为例：

```text
Hq % TP == 0

Hkv >= TP 时：Hkv % TP == 0，按KV heads分片
Hkv <  TP 时：TP % Hkv == 0，部分KV heads跨卡复制
```

此外还要满足其他层尺寸、量化格式、后端等约束；这不是所有模型实现的普遍限制表。

Qwen2.5-0.5B有14个Q heads、2个KV heads：TP2可得到每卡7个Q heads、1个KV head；标准实现不能直接用TP4，因为14不能被4整除。因此“扫TP1/2/4/8”的正确含义是**在模型支持的候选集合中扫描**，不是所有模型都照这个列表跑。[Qwen2 TP 分配源码](https://github.com/vllm-project/vllm/blob/v0.20.1/vllm/model_executor/models/qwen2.py)

### 17.13 GQA 与长上下文：每卡 KV 成本不一定随 TP 继续下降

假设模型有32个Q heads、8个KV heads，采用普通head TP：

| TP | 每卡Q heads | 每卡KV heads | KV分配 |
|---:|---:|---:|---|
| 4 | 8 | 2 | 按head分片 |
| 8 | 4 | 1 | 按head分片 |
| 16 | 2 | 1 | KV head在多个rank间复制 |

TP8→TP16时，Q heads与部分线性层计算继续减少，但每卡仍持有一个KV head的完整历史。**每卡KV容量以及逻辑读取需求不再按TP翻倍而减半。** 实际读取还受kernel内复用、缓存等影响。

对单请求、单层、K/V维度同为D、完整attention的情况，单卡逻辑KV数据规模约为：

```text
2 × 本卡KV head数 × 有效历史长度S × D × 每元素字节数
```

固定TP时，S增长会增加KV容量、每步attention需要访问的数据范围以及计算量。多请求时按各自的有效长度求和；不能把不同长度请求都简单当成同一个S。

这里必须区分两类流量：

```text
历史KV读取：本卡显存 → 本卡计算，随S增长
TP归约：各卡交换本轮输出部分和，主要取决于本轮token数和hidden尺寸
```

普通head TP不是每轮把整条历史KV在卡间传一遍。固定活跃batch、每请求本轮一个token时，S翻倍不意味着TP输出归约字节数也翻倍。若同时改变batch、缓存迁移或并行策略，需要另行分析。

当瓶颈来自长历史KV、heads难以继续切或已开始复制，可考虑适用的DCP/上下文并行：按历史位置分担KV和attention，再合并局部统计量与输出。它解决的维度与head TP不同，也引入额外通信；本项目没有据此完成新的DCP性能验证。

### 17.14 单请求更快与整套服务吞吐更高不是同一目标

**固定8卡，比较1个TP8和2个TP4。** 假定两个方案都能放下模型及目标KV，下面是普通decode每请求每轮输出一个token的教学例子，省略prefill、网络和调度变化，不是SNN或本项目实测：

| 部署 | 每副本执行的请求数 | 每轮时间 | 全系统decode输出吞吐 |
|---|---:|---:|---:|
| 1个TP8 | 16 | 10ms | 16/0.010 = 1600 tok/s |
| 2个TP4 | 每个16 | 15ms | 2*16/0.015 ≈ 2133 tok/s |

TP8下单请求约每10ms输出一个token，TP4约每15ms；但两个TP4同时推进32条请求，总输出更多。原因是4卡扩到8卡未必使一个副本速度翻倍，而两个副本能独立服务两组请求。实际还受每副本KV容量、batch、负载均衡及共享资源干扰影响。

这张表是**给定并发下的执行例子**，不是低负载单请求benchmark，也不能不经测试就换算成服务可持续QPS。请求长度、prefill成本、排队和结束规则都会影响QPS。

**加入SLO后，选择可能改变：** 若只看这个简化例子的TPOT，门限20ms时两者都通过，两个TP4可能更有容量优势；门限12ms时TP4的15ms不通过，不能只凭总tok/s高就选它。真实评估应使用指定的TTFT/TPOT或ITL分位数、成功率和联合达标请求，而不是用示例平均值代替完整SLO。

**为什么TP2低负载延迟不达标，多加副本也不能直接解决？** 假设单请求无排队地跑在一个TP2副本上，仍需30ms输出一个token，而目标是20ms。增加4个TP2副本，只会把不同请求分流到4组卡；请求A仍在其中一个TP2副本上执行，其他副本不会共同加速它的前向，所以不能直接把30ms变成20ms。

要与下面的情况区别：

```text
执行本身受限：空闲、单请求时已经30ms > 20ms
  → 增副本不直接加快该请求；需优化单副本执行/模型/并行配置等

负载导致变慢：空闲时15ms，繁忙后大batch或调度等待变成35ms
  → 增副本分流，减轻每副本压力，可能恢复到达标范围
```

副本扩展主要增加总容量、降低每副本竞争与排队；TP主要让多卡共同承担一个副本的计算。两者可以组合，但不能互相等价替代。

### 17.15 结合本项目怎样选择 TP 与副本数

以下是后续推荐测法，不代表当时已经完成全部实验：

1. **筛选合法配置与容量条件**：核对heads、其他层/量化约束、互联、权重与目标KV容量，得到可执行的TP集合。
2. **测单副本执行扩展效率**：固定模型、精度、输入长度、已缓存长度和实际batch，分别比较prefill及decode；用时间线看本地执行、通信重叠和rank等待。另测低负载单请求延迟，确认最基础的SLO可行性。
3. **测固定资源预算下的副本组合**：如8卡比较合法且放得下的TP8×1、TP4×2、TP2×4。分别调整合适的调度上限与batch，不把统一max-num-seqs当成统一实际工作量。
4. **按同一请求分布扫描到达QPS**：记录实际到达/完成、队列趋势、TTFT/TPOT尾延迟、失败率及联合SLO goodput；排除有限请求数收尾和客户端限流影响。
5. **复核边界与成本**：重复测量通过/失败边界，报告相同总卡数的容量、每卡效率，以及达标条件，不只报告一个输出tok/s最大值。

如果通信主导，优先检查拓扑映射、后端路径、慢rank和可实现的通信/计算重叠，再比较降低TP、增加副本或TP+PP。若是本地KV读取主导，则考虑上下文长度、并发、KV精度与适用的上下文并行；不能看到TPOT高就只增加TP。

面试可表述为：

> 我先判断TP配置是否合法、模型和目标KV能否放下，再比较本地计算与访存的节省是否超过新增通信成本。普通TP按head分担attention，长上下文仍会增加每卡KV读取，GQA还可能因KV复制而限制扩展收益。选部署时我会区分低负载单请求延迟和固定总GPU数的SLO容量：更大的TP可能让单请求更快，多副本可能让整体吞吐更高；如果小TP在无排队时已不达标，单纯增加副本不能直接解决执行延迟。

### 18.1 当前脚本还存在的统计工程局限

- `test_list.py` 以输出 JSON 是否存在来写 case 的 `OK`；这不等于该 case 所有请求成功，也不等于 SLO 达标。解析异常回退空字典还可能写出零值，应独立核验 completed/failed 与退出状态。
- 当前 wrapper 将中间 JSON 汇总成 CSV 后清理，未形成完善的逐请求数据留档。后续应保留原始输出、实际到达时间和 token 数；仅 CSV 汇总无法重建精确 goodput 或追踪尾部请求。
- 当前请求函数在缺少服务端 usage 时可能回退到配置输出长度，因此要核对实际输出/重分词统计，不能盲目信任分母。
- `analyze.py` 按模型混合各 IO 档，且每卡吞吐用 TP 作分母，PD 情况应修正为实际总卡数。
- 当前参数快照不等于完整环境快照，还应保存镜像/版本/启动命令/硬件/运行模式。
- 同一模型各 case 顺序运行，缓存和热状态可能延续。测冷缓存与热缓存应分开设计，避免相同输入在预热后命中 prefix cache。

以上是本次阅读中确认或需要进一步核验的限制；本文只做文档整理，没有修改这些脚本。

## 19. 面试追问速答

**Q：你做的是 K8s 调度平台吗？**

A：运行环境由已有平台提供，我实现的是容器内的测试编排，负责静态 GPU 绑定、模型服务启动、就绪检查、压测和结果归档。没有把它描述成集群资源调度器。

**Q：为什么服务层和压测层拆开？**

A：服务部署配置与工作负载扫描可以独立变化。统一 HTTP 接口后，同一个压测器可以测 TP1、TP4 或 PD 入口，也便于接入其他兼容服务。

**Q：怎么证明达到吞吐上限？**

A：不能只看有限请求测试的 req/s 平台。我会确认客户端实际到达速率，延长压测，观察完成速率、等待队列和尾延迟，区分稳定容量与满足 SLO 的可用容量。

**Q：real_concurrency 能代表 GPU batch 吗？**

A：不能。它是成功请求 E2E 总和除以测试时长，包含服务端等待。实际 GPU 工作量要看 scheduler 的 running、scheduled tokens、KV 和执行记录。

**Q：为什么调高 max-num-seqs 后 TPOT 变差？**

A：可能允许更多请求共享执行，batch 和每轮成本变大；如果吞吐收益已经很小，继续增大会降低每请求生成速度，也可能增加 KV 压力。需要结合实际调度数量，不能只看配置值。

**Q：PD 为什么没更快？**

A：这组实验 D 侧仍是4卡，观测到KV压力和排队，增加P资源没有解决主要限制，还多了交接成本。不过具体性能差不能只归因一个kernel，且8卡PD与4卡集中式需要额外做等总资源对比。

**Q：EAGLE3 接受率为什么随负载下降？**

A：记录里出现接受率降低，但没有完成控制变量验证。排队本身不会让预测变错，需要检查统计窗口、输入与生成位置、模型采样配置及数值路径。

**Q：投机第一个候选错了怎么办？**

A：单条候选链的后续上下文都失效，所以舍弃后续候选和对应无效KV；目标模型仍给出正确替代token，这轮至少推进一个token。

**Q：layerwise 的收益是什么？**

A：按层传KV，把通信与计算重叠，主要隐藏传输等待；不直接减少decode的计算量。是否能提前启动D还要满足输入token和交接条件，本项目没有证据证明已启用这种重叠。

**Q：你最有价值的发现是什么？**

A：识别出测量结果与系统能力之间的差别。例如有限请求数下，收尾时间就能让req_tp变缓，不能把它直接当容量拐点；后续需要结合队列时间序列、SLO和实际到达率建立更可靠的判断。

## 20. 后续优先补充与复习顺序

### 20.1 最值得补的四项

1. **固定一套可复现 manifest**：环境版本、实际启动命令、模型/draft、硬件、Graph/缓存/调度配置和工作负载；先让每条结果可追溯。
2. **保留逐请求数据**：计划到达、实际发送、首响应、结束、输出数、成功/失败、超时；能重算分位数、SLO goodput 和平均在飞数。
3. **实现持续闭环与定时开环测试**：分清并发扫描与到达率扫描，用稳定窗口配合排队趋势验证边界。
4. **补一个单变量执行剖析**：挑固定模型和一个异常档，对照投机开关或调度配置，记录CPU/GPU时间线、通信与KV状态，避免停留在利用率推断。

### 20.2 不需要一次背完所有源码

面试前先熟悉三条链：

```text
部署链：参数 → run_list → 可见GPU/端口 → vllm serve → 就绪
测量链：request-rate → 实际发送 → TTFT/TPOT → 汇总 → 统计局限
归因链：延迟异常 → waiting/running/KV → 阶段/通信/执行剖析 → 对照验证
```

然后掌握两组边界：配置上限不等于实际执行量；观察到相关变化不等于已证明因果。

本文中“推荐测法”和“待验证原因”可以在面试时作为复盘和改进方向介绍，不要把它们说成当时已经完成的实验结果。
