### 5. 进一步定位到 unpadding 与越界写（17:14—22:45）

**[17:14] 我：** 定位到 Attention 算子后，逐步拆分，底层有三个算子：先 padding，再 SDPA，再 unpadding。

如果开启前缀缓存，会有部分命中，也就是 KV cache block 的命中。输入 prefill 的 Q 的 sequence length，会区分成已经命中和未命中的部分。

**[17:38] 我：** 它会事先声明未命中部分的长度，把不同 request 未命中的部分拼接成一个二维 tensor。如果用多维 tensor 存储，显存利用率可能不高；拼接成二维 tensor，可以减少这种显存碎片化的情况。内部以这个拼接的二维 tensor 存储需要新计算的 Q。

计算 SDPA 时，需要通过 padding 把它转成多维 tensor，比如 batch size、head number、sequence length、head dimension 这样的四维矩阵。这一步也会把之前命中的 KV block 提取出来，跟新 Q 对应的二维 tensor 整合，再送进 SDPA 计算 Attention。

然后经过 unpadding，把新计算的 Q `[此处输出张量名称按原回答保留，待核对]` 取出来，再转回原来的二维 tensor。padding 和 unpadding 实际上做的是显存布局转换。

**[19:29] 我：** 我之前插入的检查点不会马上抛错。即使在这三个算子后面都插检查点并同步，也不一定在那个时候马上报错，可能在三个算子后面才报错。所以没办法通过检查点直接判断是哪一个算子报错。

于是使用插桩的方式，把三个算子依次替换。替换的实现只接收输入，输出对应形状的 tensor，不对数据做修改。虽然算出来的数据有问题，但不会触发那种报错，用这种方式逐个排查。

**[约20:15] 我：** 后来发现是 unpadding 算子有问题。unpadding 和 padding 是闭源的，我也没办法修改它内部实现。

分析输入时发现：正常把多个 request 新计算的 Q 的 sequence length 拼接在一起，肯定需要边界范围。比如这个长二维 tensor 的哪一块属于请求 1，哪一块属于另一个请求，需要起始点、终止点这样的参数，相当于一个数组。

但它传入时没有接收这个参数，那 unpadding 的时候就不知道怎么还原。我推测它按照最大的 max sequence length 写出去，但实际分配的只是需要新计算的 Q 的长度，于是会造成越界写，污染后面的显存。

GPU 不会马上识别这种错误，后面的 kernel 再调用这块显存时才会出现异常。

**[约21:20] 我：** 当时用 Python 层面的路径把这三个算子替代掉：取出已经命中的 KV block，把新的部分 padding 成 tensor，计算，再 unpadding 回 tensor，相当于完全绕过这三个算子。绕过以后，卡死基本消失。

还有一个小问题：卡死消失后，输出数据仍然有些问题。后来发现 ending token 没设好。正常结束 token 应该有两个，这边只配了一个，所以有些回答不会终止，因为没有识别到结束 token。补上以后，基本修复了这些问题。

**[25:20] 我：** 一开始设置的指标是每秒输出请求数。对应的输入请求数就是发压速率，表示每秒接收多少请求。我想通过输出请求数判断性能拐点：如果输出请求速率小于输入请求速率，可能存在性能拐点；如果一样，可以理解为还没到性能瓶颈。

但当时发现，无论哪种发压速率，输出请求速率一定比输入请求速率小。

**[约26:12] 我：** 当时分析，问题其实出在计算上面。

**[26:18] 我：** 问题在计算上。我当时算的时候，是用整个 E2E 延迟除以所有输出请求数目 `[这里按原回答保留，分子分母方向需回听核对]`。

E2E 延迟实际上分成第一个 request 到最后一个 request 之间的耗时，以及最后一个 request 在整个推理过程里的耗时。

比如发送 100 个 request，每个 request 需要 5 秒执行完。如果每秒发一个，E2E 就是 100 加 5。前面的 100 秒相当于流水线，每秒输出一个 request；最后的 5 秒，是最后一个 request 经过整个系统的时间。再除以 100，就天然比输入 request 小 `[该例子中的计算方向按原表达保留]`。

**[约27:25] 我：** 后来发现这个指标设置得不是很好。可以把输入请求数拉得很大，削弱最后一个请求耗时的影响。首先尽量把整个请求队列拉大；另外不再单纯用“输出 request 低于输入 request”作为瓶颈指标，而设置一个比例，比如低于 0.8，再分析是不是真的存在性能瓶颈。

**[28:09] 我：** 后来又设置了分析性能瓶颈的流程：先按发压速率，不固定一批到底输入多少请求，而在 CPU 端一直发送请求，保证整个推理框架持续接收请求，维持一定数量的请求在推理，然后不断拉高，看看吞吐有没有达到瓶颈。

正常来说，只看每秒请求输出，没办法跟 batch size 结合。假设总吞吐是固定值，拉高 batch size 后，单个请求耗时会增加。

**[约29:40] 我：** 比如两个 request 并发，总吞吐 10 tokens/s，那么两个请求各约 5 tokens/s；三个请求并发，可能各约 3 tokens/s，总吞吐 3×3，约等于 10 tokens/s。单看每个请求的输出 tokens/s，它是下降的。

所以先不断拉高发压速率，确定总吞吐。

**[30:39] 我：** 吞吐确定以后，再使用每批次 request 的请求，不断拉高发压速率，让它满足 SLO。比如设置 TTFT 小于多少、TPOT 小于多少，看看哪个 request 发压速率满足这个范围，找满足条件的最大发压速率。大概这样分两步分析瓶颈。
