# 学习笔记：Tensor Parallel 切分 与 卡间集体通信

> 记录于 2026-05-09，从一次 vllm 死锁排查中梳理出来。

## 起因

我跑了个 8 卡 TP 的 Qwen3-8B 推理，长 prompt 场景下 vllm 卡死。
排查时看到 worker 全部停在 `torch.distributed.broadcast`，开始追问：
- TP 到底怎么切的？
- 为啥每个 step 都要互相通信？
- 死锁到底是谁在等谁？

下面把这些问题串起来记一遍。

## 一、Tensor Parallel 是怎么切的

把一个 Transformer 模型放到 N 张卡上，主流方式有几种：

| 切分方式 | 切的是什么 | 通信代价 | 典型用法 |
|---|---|---|---|
| **Data Parallel (DP)** | 每张卡放整个模型，分担不同 batch | 梯度同步 | 训练 |
| **Tensor Parallel (TP)** | 把每一层的权重张量切到多卡 | 每层都通信 | 推理 / 训练 |
| **Pipeline Parallel (PP)** | 把不同层放到不同卡（流水线） | 跨卡传 hidden state | 模型超大时 |
| **Expert Parallel (EP)** | MoE 模型不同 expert 分卡 | 路由通信 | MoE 模型 |

vllm 推理常用的是 **TP**，因为：
- 推理 batch 通常没那么大，DP 派不上用场
- TP 能让一张卡装不下的大模型分散开
- 每层并行的算力提升 ~N 倍（理论上）

### TP 是 Megatron-LM 那一套切法

Transformer 每一层主要有两块：

**1. Attention 层 —— 按 head 切**

Qwen3-8B 有 32 个 attention head，TP=8 → 每张卡分 4 个 head。

```
        Q, K, V 投影矩阵 [hidden, hidden]
        ↓
        TP=8 切成 8 份：每张卡持有 [hidden, hidden/8]
        ↓
        每张卡独立算自己 4 个 head 的 attention
        ↓
        最后输出投影把所有 head 拼起来
```

**2. FFN 层 —— 按隐藏维度切**

FFN 是两层 MLP：`hidden(11008) → intermediate(28672) → hidden(11008)`。

```
        第一层 (Column Parallel)：
          权重 [11008, 28672] 沿"输出维度"切
          每张卡持有 [11008, 3584]
          每张卡独立算，输出 [B, T, 3584]    ← 这一步不需要通信

        第二层 (Row Parallel)：
          权重 [28672, 11008] 沿"输入维度"切
          每张卡持有 [3584, 11008]
          每张卡用自己那 3584 维算，输出 [B, T, 11008]
          但每张卡算的是"部分和"，必须加起来才对   ← 必须 all-reduce
```

### 一个直觉的总结

TP 的口诀是：**Column Parallel 不需要通信，Row Parallel 后必须 all-reduce**。

- Column 切完每张卡产生**互不重叠的输出**，可以接着算下一步
- Row 切完每张卡产生**部分结果**，必须求和才完整

8 卡 TP 跑 Qwen3-8B 一个 step：
- 32 层 transformer
- 每层有 Attention 和 FFN，各自的 Row Parallel 后都要 all-reduce
- **每个 token 至少 ~64 次 all-reduce**

通信开销不小，所以 TP 卡间网络带宽（NVLink / MCCL link）很关键。

## 二、卡间集体通信（Collective）

TP / DP 都依赖一类操作叫**集体通信**，常见的有：

| 操作 | 语义 | 用在哪 |
|---|---|---|
| **broadcast** | rank 0 的数据复制到其他所有 rank | 输入分发 |
| **all-reduce** | 所有 rank 的数据求和（或其他 op），结果每个 rank 都拿到 | TP Row Parallel 后 / DP 梯度同步 |
| **reduce-scatter** | all-reduce 但每 rank 只拿到一部分结果 | ZeRO 优化 |
| **all-gather** | 每个 rank 的数据片段拼成完整的，每个 rank 都拿到 | 反向传播某些步 |

### 集体通信的"对称性"

这是当时让我纠结的关键点。

**集体操作不是 client-server 那种"一方请求、一方响应"的关系。** 而是：

> **所有 rank 必须一起调用同一个集体函数，一起进入，一起返回。**

举例：8 张卡做 broadcast：

```python
# rank 0 (driver):     # rank 1-7 (workers):
broadcast(tensor,      broadcast(tensor,
          src=0)                  src=0)
```

**注意：rank 0 调用的函数和 rank 1-7 调用的是同一个**！只是 src=0 表明 rank 0 是数据源。

这和我一开始想的不一样 —— 我以为是 rank 0 调 `send()`，rank 1-7 调 `recv()`，发出去等收到。**实际不是这样**，集体操作是对等的，所有 rank 调用相同函数，库自己内部协调谁送谁收。

### 在 GPU 上是怎么实现的

底层流程（以 NCCL/MCCL 为例）：

```
1. 每个 rank 调 broadcast()
       ↓
2. 每张 GPU 把 broadcast kernel 提交到自己的 stream
       ↓
3. kernel 之间通过 GPU 内部链路（PCIe / NVLink）互相 sync 拷数据
       ↓
4. 数据传输完成，所有 rank 的 kernel 一起结束
       ↓
5. Python 层 broadcast() 返回
```

第 2 步之后，CPU 上的 Python 实际上在**自旋等待**这个 kernel 完成。这解释了为啥死锁时进程显示 `R (running)` 但 GPU 利用率却是 0% —— **CPU 在烧自旋检查 kernel 状态，但 GPU 没在算（在等通信）**。

## 三、死锁是怎么回事（重新理解）

### 我最初的（错误）理解

> "握手阶段卡死了，从机全部响应了，但主机卡在等待接收。"

这个理解错了，错在两处：

1. **broadcast 没有"握手 / 数据传输"两阶段** —— 它是一个原子调用，没有显式握手协议
2. **没有"主从等待"关系** —— 8 个 rank 是对等的，都进同一个调用，都被卡

### 正确的理解

我用 py-spy 抓了所有 8 个 worker 的 Python 栈，发现：

| Worker | 调用位置 |
|---|---|
| rank 0（driver） | `broadcast` 在 `_get_driver_input_and_broadcast`（作为发送源） |
| rank 1-7 | `broadcast` 在 `_get_worker_input_from_broadcast`（作为接收方） |

**关键观察：8 个 rank 全部到位**，没有谁掉队。

如果是经典"等不到对方"的死锁，应该是某个 worker 还卡在前一步、其他在等它。但现在所有人都进入了 broadcast，**问题不在调度层**。

### 那到底卡在哪？

```
Python 层：8 个 rank 都调用了 broadcast()        ← 没问题
   ↓
CUDA 层：8 张卡都提交了 broadcast kernel          ← 没问题
   ↓
设备层：MCCL kernel 在 8 张卡之间协同传数据       ← ★ 这里挂死
   ↓
Python 层：自旋等 kernel 返回                    ← 永远等不到




实际发生了什么                                                                                                                                                                  
                                                                                                                                                                                  
  Python 层：所有 8 个 rank 调用 broadcast()                                                                                                                                      
                ↓ 
  CUDA 层：每张卡都把 broadcast kernel 提交到自己的 stream                                                                                                                        
                ↓                                                                                                                                                                 
  设备层（卡之间）：MCCL 启动通信 kernel，                                                                                                                                        
                通过 PCIe / NVLink / 内部互联让 8 张卡协同复制数据                                                                                                                
                ↓                                                                                                                                                                 
                ★ 这里挂了                                                                                                                                                        
                ↓                                                                                                                                                                 
                kernel 没出错，没崩溃，但永远不结束
                ↓                                                                                                                                                                 
  Python 层：torch.cuda.synchronize() 风格的轮询，自旋等 kernel 完成
                → 这就是为啥 worker 都是 R (running)、CPU 烧着，但没进展  

```

**死锁发生在 MCCL 库的内部** —— 卡间通信 kernel 启动了，但 8 张卡之间的协调逻辑出了问题，kernel 既不报错也不结束。

可能的原因（按可疑度）：
1. **8 个 rank 提交的 broadcast 参数不一致**（shape / dtype / count）—— MCCL 收到不一致描述符就会挂
2. **某张卡的 buffer 还被别的 kernel 占着** —— broadcast 等不到独占访问
3. **MCCL 内部 race condition** —— 长 prompt 触发的边界情况
4. **CUDA Graph 把 broadcast 录进去了**，replay 时数据指针错乱

### 一个比喻（最后帮自己理顺）

8 个人手拉手围成一圈，约定一起说出某句话的下一个字。

- 每个人都张嘴（=进入 broadcast）✅
- 但有一个字大家约定不太一致，传到那一步全卡了 ❌
- 谁也不能合嘴，因为还没轮完一圈

**不是某个人没张嘴，是约定本身在那一步崩了。**

### 怎么定位 root cause

仅从 Python 栈看不出来，需要：

```bash
# 重启 vllm 时打开 MCCL 详细日志
MCCL_DEBUG=INFO MCCL_DEBUG_SUBSYS=COLL,INIT \
  bash run.sh /data/SETS/models/qwen3-8b 8 32768

# 复现死锁后看 server.log 里 MCCL 的最后几条
# 能看到具体哪个 collective、count 多少、buffer 啥 dtype 时挂死
```

## 四、为什么 mthreads-gmi 显示 GPU 0%

这个之前也疑惑过 —— vllm 卡住时 worker CPU 全在烧，但 mthreads-gmi 显示 GPU 利用率 0%。

现在能解释了：

| 阶段 | CPU 状态 | GPU 状态 |
|---|---|---|
| 模型 forward 计算 | 偶尔忙（提交 kernel） | 高（在做矩阵乘） |
| 集体通信中 | **持续忙**（自旋等 kernel） | **几乎空**（只有 MCCL kernel 在做轻量数据移动） |
| 卡间通信死锁 | **持续忙**（自旋永不退出） | **接近 0%**（MCCL kernel 没在搬运任何东西） |

**mthreads-gmi 测的是矩阵计算单元的利用率**，不是"GPU 是否有任何 kernel 在跑"。MCCL 通信 kernel 即使在跑，也不会让 %GPU 这个指标涨多少 —— 它根本不算东西。

这也是为啥推理时即使一切正常，多卡 TP 的 %GPU 看起来也比单卡低得多 —— 一大段时间都花在卡间同步而不是计算上。

## 六、收获 / 提醒自己

1. **集体通信是对等的**，没有主从概念，8 个 rank 都要进同一个调用
2. **多卡推理的 GPU 利用率天然低**，因为大量时间在卡间通信
3. **vllm 卡死时一定要看 py-spy 全部 worker 的栈**，对比着看才能区分"调度问题"和"通信问题"
4. **mthreads-gmi 的 %GPU 不可单独信**，要配合 server.log 的 throughput 一起看
5. **MCCL 死锁不是 vllm 调度 bug**，是底层通信库 bug，要靠 `MCCL_DEBUG=INFO` 才能定位
6. **TP 切的是权重不是数据**，每张卡看到完整 batch，只是各算一部分维度
7. **CUDA Graph 在多卡通信场景下有兼容性风险**，遇到诡异死锁优先关掉 `--enforce-eager` 试试

## 七、Gather collective 的完整调用链

以 8 卡 TP 推理 Qwen3-8B 时 logits gather（count=18992 fp16）为例，完整数据流穿过 6 层。

### 调用链全景

```
torch.distributed.gather(input, outputs, dst=0)              [Python 层]
        ↓
ProcessGroupMCCL::gather                                     [C++ 适配层]
        ↓ 拆成 7×Send + 7×Recv
mcclSend / mcclRecv                                          [MCCL C API]
        ↓ 多个 op 进入内部队列
mcclEnqueueCheck                                             [MCCL 入队检查]
        ↓ 参数 / 通信器 / 调度器验证
ncclLaunchKernel → musaLaunchKernel                          [GPU stream 提交]
        ↓
__global__ ncclKernel                                        [Device 端]
```

### 各层职责

**第 1 层：`torch.distributed.gather`（Python）**
- 用户面向 API，不实际传数据
- 检查参数（shape / dtype / device 一致）
- 找到 process group 调用对应 backend

**第 2 层：`ProcessGroupMCCL::gather`（C++ 适配）**
- MCCL 库**没有原生 gather**，只有 Send/Recv 等点对点原语
- 把 1 个 gather 拆成 N-1 个 Send + N-1 个 Recv：
  - rank 0：`mcclRecv from peer=1, 2, ..., 7`（共 7 次）
  - rank 1-7：每个 `mcclSend to peer=0`
- 这就是日志里看到 `count=18992` 出现 14 次的原因

**第 3 层：`mcclSend / mcclRecv`（MCCL C API）**
- 不立即执行，把 op 加入内部队列
- 选择算法（小数据 / 大数据走不同 protocol）
- 准备 kernel launch 参数（gridDim、blockDim、shared memory）
- NCCL/MCCL 会**攒一组 op 打包成单个 kernel**（group call 优化），减少 launch 次数

**第 4 层：`mcclEnqueueCheck`**
- 通信器（comm）状态检查
- op 参数互相匹配验证（你 send 18992 我也得 recv 18992）
- stream 健康检查
- 调度槽位可用性
- 通过后输出 `mcclEnqueueCheck isAsync:1`

**第 5 层：`ncclLaunchKernel` → `musaLaunchKernel`**
- 把 kernel 提交到 GPU stream
- 提交成功会输出 `params->gridDim:..., params->blockDim:...`
- 调用是异步的，立即返回；GPU 后续在 stream 上执行 kernel

**第 6 层：device 端 ncclKernel**
- SM 上跑的协调程序，负责：
  - 跨卡握手（信号量同步）
  - 数据 P2P 拷贝
  - 多 chunk 流水线调度

## 八、为什么搬运数据需要 kernel

GPU 的硬件实际上有两条独立的"腿"。

| | DMA 引擎（copy engine） | SM（流处理器） |
|---|---|---|
| 职能 | 单向连续内存搬运 | 跑 kernel（既能算也能搬） |
| 调用方式 | `cudaMemcpyPeer*` | `<<<grid, block>>>kernel(...)` |
| 能否做条件分支 / 同步 | ❌ | ✅ |
| 能否访问信号量、原子变量 | ❌ | ✅ |

单纯的 GPU-to-GPU 内存复制，DMA 就够，不用 kernel。但 collective 通信不是单纯复制：

1. **多 GPU 之间的同步**：rank 0 必须知道其他 rank 数据何时就绪。需要轮询 / set flag。DMA 引擎不能 set flag、不能轮询。SM 上的 kernel 可以。

2. **多步流水线**：大 tensor 切 chunk 流水化传输，每个 chunk 依赖上一个完成。这种状态机只能 kernel 跑。

3. **拓扑路由**：ring allreduce 数据要绕一圈，每张卡既是接收者又是发送者，中间还要做 reduce。DMA 没这能力。

4. **allreduce 的真实计算**：`SUM` / `MAX` 是真的算，DMA 不能算。

NCCL/MCCL 为了**算法统一**，所有 collective 都用 kernel 实现，包括 gather/broadcast 这种"看似纯搬运"的操作。kernel 在这里的角色更像"GPU 上的协调程序"，绝大部分指令在等信号量和搬数据，真正的"计算"很少。

## 九、Device 端握手机制

### 实现方式：global memory 上的原子变量

```cpp
__device__ uint64_t* flag;   // GPU 内存里的标志位
__device__ float*    data;

// rank 1 (producer)
*data = my_value;
__threadfence_system();      // 内存屏障，保证 data 全局可见
atomicAdd(flag, 1);          // 原子置位

// rank 0 (consumer)
while (atomicAdd(flag, 0) == 0) { /* busy spin */ }
__threadfence_system();
val = *data;
```

### SM 占用问题

GPU 在 SM 上 spin 等 flag 时，确实占用 SM。这是 GPU 通信和 FPGA 通信的本质架构差异：

| | FPGA 上的握手 | GPU 上的握手 |
|---|---|---|
| 介质 | 寄存器（专用 IP，独立硬件） | global memory 里的原子变量 |
| 通知方式 | 中断 / done 信号 | 远端 SM 自旋读 |
| 占用计算资源 | 0 | 每个 channel 占 1 个 thread block |

**NCCL 的工程权衡**：
1. 一个 collective 只用 1-4 个 channel × 1 thread block，**绝大部分 SM 不受影响**
2. spin 内部带超时机制，避免死等
3. 用 `__threadfence_system` 内存屏障替代真正的硬件中断

实测 8 卡 TP 推理时，collective 占用约 1-2 个 SM 等握手；剩下 100+ SM 可以并行跑其他 kernel。但当前 collective 没完成时，**模型 forward 的下一步 kernel 没法 launch**，所以多卡 TP 的整体 GPU 利用率天然比单卡低。

## 十、Kernel 怎么访问远端 GPU 内存

GPU kernel 看到的是**虚拟地址**，地址背后可能是本地显存、PCIe 总线、或另一张 GPU 的显存。这些映射由 host 在初始化阶段建好。

### Peer-to-Peer 内存映射机制

物理布局：
```
GPU A 显存（物理）：0x1_0000_0000 ~ 0x1_4000_0000
GPU B 显存（物理）：0x2_0000_0000 ~ 0x2_4000_0000
```

Host 端调 `cudaDeviceEnablePeerAccess(B, A)` 后，CUDA driver 通过 **PCIe BAR 映射**把 GPU B 的物理地址放进 GPU A 的虚拟地址空间：
```
GPU A 上 kernel 看到：
  本地地址 0x7fff_0000_0000  → 物理 GPU A 显存（走自己 cache）
  远端地址 0x7eee_0000_0000  → 物理 GPU B 显存（走 PCIe / NVLink）
```

### Kernel 内 P2P 写

```cpp
__global__ void send_kernel(float* local_buf, float* remote_buf, int n) {
    int i = threadIdx.x + blockIdx.x * blockDim.x;
    if (i < n) {
        remote_buf[i] = local_buf[i];   // ← 这一行就是 P2P 写
    }
}
```

`remote_buf[i] = ...` 编译后是 PTX 的 `st.global.f32 [remote_buf], val`：
- GPU A 内存控制器看到目标地址在远端
- 自动通过 PCIe BAR / NVLink 把数据写到 GPU B 显存
- GPU B 完全不参与 —— 是 GPU A 的内存子系统 + 互联硬件做的

### 各阶段责任划分

| 阶段 | 谁做 |
|---|---|
| 设置 P2P 映射、申请 buffer、分配地址 | **host (CPU)**：调 CUDA driver |
| 实际数据传输 | **device hardware**：内存控制器 + PCIe BAR + NVLink |
| Kernel 决定搬哪段 | **device (kernel)**：通过预先填好的 work descriptor 读出地址 |

### NCCL 内部的工作分配

启动时（host 阶段）：
1. 每张 GPU 申请一片 comm buffer
2. 互相交换 buffer 的远端地址
3. 把当前 op 的 buffer 指针、count、peer 信息写到 GPU 内存里的 `NcclWorkArgs` 结构体
4. launch kernel，结构体地址作为参数

到了 kernel 内（device 阶段）：
```cpp
__global__ void ncclKernel(NcclWorkArgs* work) {
    if (work->op == SEND) {
        float* src = work->local_buf;
        float* dst = work->remote_buf;   // 已映射好的远端 GPU 地址
        for (int i = ...) dst[i] = src[i];   // 直接 P2P 写
    }
    // 然后做 Q1 那种握手同步
}
```

**关键**：kernel 不直接调 PCIe 接口。它只是写远端虚拟地址，PCIe 硬件把这个写操作物理实现。"对外接口"由 host 配置，但**访问由 device 完成**。

## 十一、流水线如何在 device 端实现

NCCL 把大 tensor 切 chunk，kernel 内部循环处理：
```cpp
__global__ void ncclSendKernel(NcclWorkArgs* work) {
    for (int chunk = 0; chunk < total_chunks; chunk++) {
        // step 1: 等上一轮 ready
        while (peer_flag[chunk-1] != READY) { }

        // step 2: 拷贝当前 chunk 到对端
        for (int i = ...) remote_buf[chunk] = local_buf[chunk];
        __threadfence_system();

        // step 3: 通知对方"我这 chunk 好了"
        my_flag[chunk] = READY;
    }
}
```

整个流水线全在 device 上跑：
- "决定搬哪段" = 循环变量 + 预先填好的 buffer 指针
- "通知对方" = 远端 flag 写
- "等对方" = 远端 flag 读自旋

## 十二、FPGA 视角的架构对比

|  | FPGA 通信 | GPU NCCL 通信 |
|---|---|---|
| 握手介质 | 专用寄存器 / shared memory IP | global memory 上的 atomic flag |
| 通知方式 | 中断 / done 信号 | 远端 SM 自旋读 + memory fence |
| 数据搬运 | DMA 引擎（独立硬件） | PCIe BAR + 远端写 store 指令 |
| 状态机 | 独立的 control IP | kernel 内部循环 + flag 轮询 |
| 控制与数据通路 | **分离**（不互相占用） | **共享**（SM 是通用控制器+计算单元） |
| 占用计算资源 | 0 | 每个 channel 1 thread block |

最大概念差异：**GPU 没有独立的"控制硬件"**，所有控制逻辑必须借 SM 跑（kernel）。这是 GPU 灵活性的来源（不用为每种通信模式做新硬件），也是 SM 占用问题的根源。

## 十四、vLLM 优化:默认开 vs 显式启用

我们之前跑指令一直在显式控制 prefix-caching（`--enable-prefix-caching`），那是不是 vLLM 所有优化都要这样显式开?**不是。** 规律是:**白送且无风险的默认开;有数值风险/有副作用/要额外资源的默认关**。

### 默认就开,关不掉(算法地基)

| 优化 | 状态 | 说明 |
|---|---|---|
| **PagedAttention** | 永远开 | vLLM 地基,KV cache 分页存储,没有开关 |
| **Continuous batching**（连续批处理） | 永远开 | 调度器核心,请求动态进出 batch,也是地基 |
| **CUDA Graph**（MUSA 上是 musa graph） | 默认开 | `--enforce-eager` 才是**反向关**它(run.sh 里 `ENFORCE_EAGER=0` 即走 graph) |

前两个是 vLLM 快的主因,白送。CUDA Graph 是唯一"默认开、要反向关"的特例。

### 默认关,必须显式启用(加 flag)

| 优化 | 启用方式 | run.sh 现状 |
|---|---|---|
| **Prefix caching** | `--enable-prefix-caching` | ✅ 已显式控制(`ENABLE_PREFIX_CACHING`) |
| **Chunked prefill** | `--enable-chunked-prefill` | ❌ 注释里有,没开(V0 兼容性差) |
| **量化 KV cache** | `--kv-cache-dtype fp8` | ❌ 注释里有,没开 |
| **权重量化** | `--quantization fp8` 等 | ❌ 需要量化过的模型 |
| **投机解码** | `--speculative-config '{...}'` | ❌ 需要额外的小草稿模型 |
| **Pipeline 并行 PP** | `--pipeline-parallel-size N` | 我们设 =1(等于没用) |
| **Expert 并行 EP** | `--enable-expert-parallel` | ❌ 只对 MoE 模型有意义 |
| **Disaggregated prefill**（P/D 分离） | `--kv-transfer-config '{...}'` | ❌ 要多实例编排 |

### 一句话总结

- **算法地基**(PagedAttention、continuous batching)→ 焊死,无开关。
- **会改数值 / 有副作用 / 要额外资源** → 默认关,必须显式加 flag。prefix-caching、chunked-prefill、量化、投机解码全属此类。
- **CUDA Graph** → 例外,默认开,用 `--enforce-eager` 反向关。

> 设计逻辑:**白送且无风险 → 默认开;有数值风险或要额外东西 → 默认关,决定权交给用户**。
> 我们折腾的 prefix-caching 正好是"默认关、需显式开、且在 vllm_musa 上有 OOB bug"那类——最需要显式控制。

### 和本项目的关系:LMCache 更"难启动"

LMCache 也属"需显式启用"那类,但更进一步:不光要 flag(`--kv-transfer-config`),还**强制要求 V1 引擎**。而 V1 在 S5000(PH1, arch 310)上跑不起来(`flash_attn_varlen_func` kernel 未适配),所以 LMCache 比上表任何一个都更难启动——这也是我们当前 LMCache 性能测试被卡住的根因。详见 `ISSUE_vllm_musa_broadcast_deadlock.md` 的 V1 引擎章节。
