## 二、还没写的题

按"能学到新机制"排,不是按刷题顺序。

### 1. Matrix Transpose —— 性价比最高,先写这个

半小时能写完。新概念不多(bank conflict 在 GEMM 里已经吃透了),但**失效模式和 GEMM 不同**:GEMM 是 shared 读冲突,transpose 是**写全局时不合并**。经典解法 `__shared__ float tile[32][33]` 那个 +1 padding。

面试问 transpose 基本就是问这个,也是 LeetGPU 第一梯队里唯一还没做的基础题。

### 2. Prefix Sum (Scan) —— 新机制密度最高

不要当成"reduce 的兄弟题",它比 reduce 难一个层次:reduce 是收敛,scan 每个位置都要输出,跨 block 时必须解决**顺序依赖**。三层:

- warp 内:`__shfl_up_sync`(warp 级原语,目前所有 kernel 都没用过)
- block 内:Hillis-Steele vs Blelloch(work-efficient,2n 次操作 vs n log n)
- 跨 block:两趟 scan,或者 **decoupled look-back**——单趟,block 之间靠 `volatile` 标志位 + `__threadfence()` 传前缀

最后那个会逼着面对**内存序和 fence 语义**,这是目前整个练习集里完全空白的区域。CUB 的 `DeviceScan` 就是这么实现的。

### 3. Causal / Flash Attention —— 是手感训练,不是学新东西

Qwen 引擎里 FA V1/V2 + FlashDecoding 都写过。再写一遍的价值在"限时不开 IDE 一次写对",按自己定的执行原则,**按训练安排,别当学习任务**。

### 4. 第二梯队融合算子 —— 碎片时间

Fused Residual+RMSNorm、RoPE、SwiGLU、GQA、LayerNorm、Top-p Sampling。写起来快,面试能直接引用项目,但机制上都是已会内容的重新组合。

里面唯一有新东西的是 **INT8 Quantized MatMul**:`dp4a` / `mma.s8` 指令、per-channel scale 的放置位置、累加器用 int32。和下面的 Tensor Core 是一路的,连着写。

## 三、GEMM 上还没做的优化

现状:**1670 GFLOP/s**,cuBLAS **13691**(超过 FP32 峰值 10944,证明用了 tensor core)。差的 8 倍不在 tiling 上。

按收益排:

### ① 向量化访存 —— 最大的非 tensor core 收益

SASS 现状:

```
312  LDG.E.U16.CONSTANT     全局加载,一次 2 字节
 56  STS.U16                写 shared,一次 2 字节
128  LDS.64                 读 fragment,一次 4 个 half
256  STG.E.U16              写回,一次 2 字节
```

一条 `LDG.E.128` 能搬 8 个 half,指令数砍到 1/8。代价是 tile 分工要重排(BK=8 时一行正好 16 字节,一个线程一行),K 不是 8 的倍数时尾巴单独处理。

**注意:RMSNorm 上实测 128 位反而比 32 位慢**(见第四节),GEMM 上大概率不同(那边是计算受限),但**要实测,别照搬结论**。

### ② double buffering + `__launch_bounds__(block_size, 2)`

已量过:127 寄存器、0 spill、5,739,101 cycles,比单缓冲快 0.9%。

**两个必须一起上**,单独任何一个都是负收益:
- 只加双缓冲 → 寄存器涨到 167,占用率掉,变慢
- 只加 launch_bounds → 没有可隐藏的延迟,白限制

`gemm_duble_buffer.cu` 目前还是 `gemm.cu` 的副本,双缓冲没动。

### ③ `cp.async`(SM80+,3060 支持)

直接解决 LDG→寄存器→STS 的中转问题:

```cpp
__pipeline_memcpy_async(&A_mem[nxt][i], &input_a[...], 16);
__pipeline_commit();
...compute on A_mem[cur]...
__pipeline_wait_prior(0);
```

global→shared 直通,**不经过寄存器**。那多出来的 44 个寄存器、STS 基址寄存器从 1 个涨到 6 个,全都没了。这是双缓冲"本来该有的样子",Ampere 之前做不到。依赖 ② 的形状,做完 ② 再做。

### ④ Tensor Core(`mma.sync` + `ldmatrix`)

8 倍差距的来源,工作量最大,对推理方向价值最高。

底下每一层都已经吃透(tiling、bank conflict、register blocking、双缓冲、ptxas 寄存器压力),缺的是最上面:`ldmatrix.sync.aligned.m8n8.x4` 按 fragment 布局灌寄存器,`mma.sync.aligned.m16n8k16` 做 16×8×16。还要用 **swizzle 代替 padding**(padding 会破坏 `ldmatrix` 要的地址规律)。

## 四、已确立的技术结论(别重新踩)

### fp16 类型

- **没有 `half4`**。CUDA 12.9 头文件里搜不到。只有 `__half2`(4 字节,对齐 4),它有真硬件指令 `HADD2`/`HMUL2`/`HFMA2`
- 要 16 字节:`struct __align__(16) half8 { __half x[8]; };`。`__align__(16)` **不能省**,否则退化成 8 条 `LDG.U16`
- **成员必须写 `__half x[8]`,不能写 `__half2 h[4]`**。后者即使对齐 16、纯拷贝、什么都不干,照样拆成 4 条 32 位加载。实测过,是类型本身的问题,不是访问方式
- 初始化:局部变量 `= {}` / `{}` / 聚合初始化都行。`__device__` / `__constant__` 只能用 `{}` 或 `__half_raw{0x3c00}`——**初始化表达式里出现函数调用就报 dynamic initialization**(`__float2half(1.f)`、`(__half)1.0f` 都算函数调用)
- 加自定义构造函数**不会**破坏向量化(实测仍是 `LDG.E.128`),代价只是失去聚合初始化语法

### 访存写法

**整个结构体读出来 → 向量化;按 `.x` / `.y` 成员访问 → 逐个 16 位。**

```cpp
h2[i].x, h2[i].y              // 2 条 LDG.E.U16   ← 慢
half2 v = h2[i]; v.x, v.y     // 1 条 LDG.E       ← 快
__half22float2(h2[i])         // 1 条 LDG.E       ← 一样快
```

关键不是"转成 float",而是**按值使用整个对象,强迫编译器 materialize 完整的 4 字节**。RMSNorm 上这一处值 **14%**。

一旦落进寄存器,`.x` / `.y` 只是寄存器半字段选择(`.H0_H0` / `.H1_H1`),零开销。

### `#pragma unroll` 与 local memory

- **动态下标 = 编译期算不出常数的数组下标。** SASS 没有 `R[i]` 寻址方式,寄存器不可按运行期下标寻址,所以这种数组只能掉进 **local memory**(thread-private,物理上是显存)
- 表现:ptxas 报 `N bytes stack frame`,SASS 里出现 `LDL` / `STL`
- **`stack frame` ≠ `spill`**。spill 是寄存器不够被迫外倒;stack frame 是这个数组从一开始就没资格待在寄存器里。两者都落 local memory,原因完全不同
- 实测:GEMM fragment 循环关掉展开 → 288 字节 stack frame(= `A_temp[8]×2 + B_temp[8]×2 + data[8][8]×4`),内层变成 3 条 `LDL` + 1 条 `FFMA` + 1 条 `STL`。展开版 512 条纯 FFMA,零 LDL
- **shared / global 的动态下标是合法的**(`STS [Rbase+imm]`),所以 staging 循环不写 pragma 没有 local memory 风险,它只是个调优旋钮
- 想真正展开,trip count 必须是编译期常量。`for(i = offset; i < 1024; i += 256)` 编译器无法证明跑 4 次(证明不了 `offset < 256`),加 pragma 也只能展开 4 次 + 余数循环。改成 `for(t = 0; t < APT; ++t)` 才是直线代码

### 数学函数

- **`powf(x, 2)` 不会被折叠成 `x*x`**(默认 `-O3` 下 96 条指令 vs 24 条)。原因不是语义不同,而是实现路径是 `exp2(y*log2(x))`,和 `x*x` 在 **6.25% 的输入上差 1 ulp**,折叠是改变结果的变换,IEEE 严格模式不允许
- `--use_fast_math` 会折(96→24),但它是整个编译单元的开关,顺带打开 `--ftz=true`、`--prec-div=false`、`--prec-sqrt=false`,还把 `sinf`/`expf`/`logf` 全换成近似版。为一个平方不值
- **规律:指数是编译期已知的小整数,手写乘法。`pow` 是给运行期指数用的**
- RMSNorm 上实测,`powf` 版比 `fmaf` 版慢 **1.72 倍**(DRAM 流量完全相同,差的全是 ALU)

### 寄存器

- 静态分配,编译期决定,整个 block 生命周期固定。ptxas 报的是**峰值同时活跃数**。**运行期不能释放**
- 内部复用只在活跃区间不相交时发生。`{}` 作用域**无关**(实测 39 vs 39)
- ptxas 倾向**重算**而不是保持(值便宜就重算)
- **3060 的寄存器悬崖:256 线程 × 128 寄存器 = 32768 = 65536 的一半,所以 128 寄存器是 2 blocks/SM 的门槛**
- `__launch_bounds__(threads, minBlocksPerSM)` 是**硬约束**,ptxas 会为了满足它而 spill
- 唯一的硬件例外是 Hopper 的 `setmaxnreg.inc/dec.sync.aligned.u32`(SM90,warp specialization)

### bank conflict

- B 矩阵按 `[n][k]` 存、读 `B_mem[(tx*8+i)*BK+k]` → bank = `(tx*32 + i*4 + k/2) % 32`,**和 tx 无关** → 16 路冲突
- 转置成 `[k][n]`、读 `B_mem[k*BN+tx*8+i]` → bank = `(tx*4 + i/2) % 32` → 2 路,且 8 个连续 half 合成一条 `LDS.128`
- 实测 857 → 2374 GFLOP/s(**2.8 倍**)
- A 矩阵没这个问题,因为它的下标里没有 `threadIdx.x`(warp 内广播)

### 同步

- `__syncthreads()` 是 **block 级**(`BAR.SYNC`),不是 warp 级。`__syncwarp()` 才是 warp 级(`WARPSYNC`,Volta 独立线程调度之后必需)
- 必须被**所有线程**到达,放在发散控制流里是 UB
- ptxas 输出的 `used N barriers` 是硬件 barrier 资源数

### 测量纪律

- **这台笔记本 GPU 的墙钟时间会因为热降频漂 ±20%**,同一个二进制在两次运行之间能反转排名(踩过:双缓冲"快 12%"是假的,锁频后单缓冲反而更快)
- 一律用 `ncu --clock-control base` + `sm__cycles_elapsed.avg`,可复现到 ±0.1%
- 判断还有没有优化空间看 `dram__throughput.avg.pct_of_peak_sustained_elapsed`,**超过 80% 就别再碰访存宽度了**

## 五、悬而未决

**RMSNorm 上 `h2[i].x` 改成整体读值 14%,机制没查清楚。**

确定的:加载指令条数正好 2 倍(第一性原理算出 1,048,576 vs 524,288,和 ncu 实测完全吻合);效果真实,锁频测三次都是 13-14%。

推翻的四个假设:

| 假设 | 证伪证据 |
|---|---|
| L1 数据阵列带宽被重复 sector 吃掉 | 微基准撑住 2.89 sector/SM/cycle > 真实 kernel 的 2.21,零代价 |
| LSU/MIO 指令队列背压 | 加 barrier 制造成簇发射后,两版只差 1.2% |
| 第二个循环命中 L1、没有 DRAM 延迟遮掩 | 二分显示改哪个循环都行 |
| ptxas 软件流水(带谓词预取) | 最快的变体一条带谓词 LDG 都没有 |

最反常的是**非线性**:改一个循环和改两个循环一样快(221K / 226K / 225K),而 v1 独自在 253K。sector 数是线性的,cycle 数不是。任何吞吐资源模型都预测中间值,实测不是。

下一步工具:`smsp__pcsamp_*` PC 采样,定位到具体哪几条指令在等什么。

**结论的适用范围:这个改动在 RMSNorm 上可信(数字可复现、正确性逐位验证),但不知道能不能迁移到别的 kernel。** 写 transpose 或做 GEMM 向量化时如果同样的模式再出现,两个数据点一起看更容易看出规律。


- cmd 里跑当前目录的 exe 要写 `.\xxx.exe`
- MSVC 输出是 GBK,管道里过一道 `iconv -f GBK -t UTF-8`
- `echo` 里不能出现 `->`,`>` 会被当成重定向

### 各目录的测试工具

**GEMM/**
```
gen_gemm  <M> <N> <K> <alpha> <beta> <seed> <out.txt>
check_gemm <input.txt> <output.txt> [samples]
```
格式:`M N K alpha beta`,然后 A(M×K)、B(**N×K,即 Bᵀ**)、C(M×N)。值在 0.25 网格、|v|≤1,fp16 精确,fp32 累加在 |结果|<128 时也精确 → **可以做逐位验证**。

**RNSNorm/**
```
gen_rms   <M> <N> <seed> <out.txt>
check_rms <input.txt> <output.txt> [rel_tol]
run_rms.bat                            # 一键跑完四组
```
格式:第一行 `M N`,之后 M 行每行 N 个值。值在 0.25 网格、[-4,4],fp16 精确。**N 必须是偶数**(kernel 按 half2 写输出)。

已生成:`input_4_8` / `input_200_100`(N=100 不是 8 的倍数,压 padding 路径)/ `input_64_4096` / `input_1024_4096`。

checker 默认容差 2e-3 ≈ fp16 舍入步长(2⁻¹¹ = 4.88e-4)的 4 倍。**实测四组的最大相对误差都是 4.7e-4**,说明误差全部来自写回 half 的舍入,kernel 本身没引入额外偏差。
